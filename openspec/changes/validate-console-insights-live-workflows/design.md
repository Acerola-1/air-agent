# Design

## Context

动机见proposal。当前业务基线来自Change6提交`2a66945`及本轮Change7补修；执行时重新冻结实际Agent/IAM的HEAD、迁移head、依赖锁、官方镜像digest及配置形状，不能把这些历史值当作现用环境。当前公开图为`basic-qa`、`data-analysis`、`intelligent-tracing`；实际入口以执行时`langgraph.json`为准。

已观察到的实现入口：`app/demand_insights/{worker,classifier,delegations,jobs,privacy}.py`、`/agent/{console,insights}/**`、`operations/insights/**`、迁移0028/0029、`insights_restore_guard.py`。本轮合成测试覆盖业务规则、RLS、租约/作业/删除边界，不证明真实身份服务、模型质量和浏览器全链。作者Embedding合成样本100%结果只作为历史参考，不作为真实分布保证。

## Goals / Non-Goals

**Goals:** 把现有6/7验收缺口转成可重跑、可定位的三个阶段；每阶段完成后独立交付结果，失败能关联到源码和固定输入。

**Non-Goals:** 扩写新业务、重写IAM、重建评测平台、重做MCP服务端、自动提取正式历史、用真实库故障注入；本次规划不执行任何阶段。

## Decisions

### D1. 分阶段启动，避免一次任务混合所有验证

| 阶段 | 回答的问题 | 输入与环境 | 启动条件 |
|---|---|---|---|
| A 系统联通 | 实际服务能否完成既定业务流程？ | 合成输入，隔离真实Java IAM、官方API/PG/Redis、后台与worker；先用受控模型/MCP | 用户另行启动本计划A阶段，资源配置核对完成 |
| B 真实案例效果 | 实际提问能否被准确分类并产生可信榜单？ | 用户批准范围的脱敏案例，批准的真实Embedding/辅助LLM；隔离分析库 | A通过；另行明确案例范围、脱敏输出、模型服务与费用上限 |
| C 性能 | 固定规模下是否达到原设计响应目标？ | 专用合成规模库，固定机器/并发，分开测本地与外部等待 | A/B完成后，用户明确启动C；默认命令不能隐式包含压测 |

拒绝用一次“一键全测”自动启动B/C。测试失败保留原始输入/日志/版本；修代码后用新目录复跑，不能只更新汇总。

### D2. A阶段用真实服务和合成内容，先解决接线与安全

1. 协调者核实IAM当前权限目录。如仍缺`agent:insights:manage`，先在IAM独立变更中提供目录迁移，再用正常管理接口创建合成账号/企业/角色、授权与回收。若无注册API，不要求实施者虚构调用或改正式root；测试正向与拒绝路径均真实内省。
2. 跑“启用→新问题确认受理→worker归类→标准问题/主题榜→来源→纠错→删除→刷新”，每一步保存关联request/source/intent/cluster/assignment及SQL期望。至少覆盖一问两意图、多attempt/resume、晚确认、缺内容后补齐。
3. 队列等待后撤权、第一次请求后重试前撤权、模型已发后删除/取消/租约接管：后续外呼为0，迟到结果不能提交。记录网络发送计数，不能仅靠403截图；所有负例有合法正向控制。少量并发正确性测试与压力测试分开。
4. 在最终锁/官方镜像各运行三个公开图；终答快照与用户看到的版本一致，溯源内部专员不增加问题量。受控模型与真实配置模型结果分别标明。
5. 真浏览器验证A→B→A、过期/503、普通修订409、来源正文清空、窄屏键盘/IME；界面与SQL互相核对，不用静态检查冒充。
6. 自有库备份→删除→恢复旧备份→先重施最新墓碑、权限/保留期/委托有效期→清理→才开放页面/worker。仅有恢复保护脚本不算演练通过。包含已过期来源、旧原型和正在重算任务。

安全与删除反例任一失败，则A不通过；修复属于对应业务域，不用放宽要求解决。

### D3. B阶段固定案例与标签，再运行真实模型

先由用户选择或批准案例来源。优先用用户编写的真实业务场景，若要用历史提问，必须单独确定时间/企业/字段范围；本计划本身不授权自动读取、导出或外发历史。原始案例留本机受控目录，Git只提交脱敏合成替代或无原句统计。

至少160条有标签的中文案例，60条校准/100条冻结留出，按语义家族划分防止同模板近重复同时进入两组；标注query/cause/forecast等动作、对象/否定/时间、应合并/不应合并、多意图/上下文不足/敏感拒绝。至少30个困难近似对照。冻结标签与内容hash后才调参；留出组不能反复调阈值。版本变化重新建profile，不混用向量空间。

沿用7的要求：自动归类precision≥98%、清晰意图覆盖≥60%、至少50项自动归类、查询/原因/预测关键误合并0；另外展示样本量/区间、逐项误合并与未归类，不能以全部拒绝提高precision。Embedding、规则拆分、LLM拆分/消歧分别报告，输入隐私和失效写回另列。达到样本分数不等于生产保证。

### D4. C阶段最后进行，不以优化代替测量

沿用原6/7的设计规模与指标，冻结资源规格、PG配置、索引、冷/热状态、数据分布和错误率：

- 6：10万request/30万attempt/100万观测，35次×2轮、并发10；本地列表P95≤500ms、聚合≤1500ms、正文≤500ms。
- 7：10万request/20万intent/1000簇，35次×2轮；榜单本地P95≤1000ms、列表≤500ms，候选容量边界另作正确性验证。
- SQL/API与IAM/模型/Langfuse等待分开；503/超时样本不能从延迟或错误率分母移除。模型调用量、预算与未知usage独立报告。

只有定位实际瓶颈后再提出最小优化；若需要预聚合/缓存或改数据模型，另给具体设计及删除/版本正确性影响，不在验收中顺手扩写架构。

### D5. 证据和遗留事项一对一管理

映射见acceptance-map.md。每个场景记录：固定输入ID/hash、预期、实测、执行层（fixture/真实服务/真实模型/浏览器）、版本、耗时、资源所有者、证据路径、局限和复跑命令。状态只用通过/失败/未执行/受阻；未执行和用户同意后置均不是通过。

小型报告提交Git；敏感原文、口令、会话、完整dump和大日志留忽略目录。删除测试用本地合成标记，任何日志不得夹带正式Token。实施/验证/外部等待分别实测，Token不可得写未采集。归档6/7前按映射明确关闭或取得用户对具体剩余项的接受，不能仅因本计划建立就自动归档。

### D6. 与既有Basic QA性能测试共用执行工具

性能口径以`docs/testing/basic-qa-performance-regression.md`及其报告模板为准。本计划不复制或重定义P（受控依赖）/E（真实配置端到端）、S（冒烟）/R（版本回归）/F（容量与发布）标准。A可复用P/S的单请求冒烟，其性质仍是功能联通，不自动启动C的规模或负载测试。Basic QA题库只覆盖一张图，其余两图仍需独立代表场景。

| 可共用部分 | 共用方式 | 必须保留的边界 |
|---|---|---|
| 资源与身份 | 一次建立自有IAM/PG/Redis/官方API/BFF、合成企业账号与资源清单 | 不把正式栈当测试环境，不绕过实时授权 |
| 问题发送与运行采集 | 固定40题`bqa-reference-202605-v1`，按原规范走BFF受理/流式/终态；统一关联ID和采集器 | 不自由换题，不把Skill答案或gold传给模型；P不证明真实模型质量 |
| 6的统计、7的增量归类 | 同一批已受理请求经正常worker流转；排空后对照预期清单查页面/API/SQL | 预期来自独立输入清单，不以被测聚合SQL自身作为答案；请求/attempt/intent/用户分别计数 |
| B质量样本 | 复用适合的题目和标注工具，再补足至少160条及语义家族隔离的60/100分组 | 40题重复四次不是160个独立案例；Q1–Q4性能类别不是问题簇；真实案例另获批准 |
| C采集与报告 | 复用同一工具、机器资源采集和证据索引 | 聊天S/R/F、后台规模SQL、组合负载分别出结论，不能相互代替 |

统一清单至少记录campaign_id、case_id、测试侧cohort、轮次、输入版本/hash，以及实际submission/request/attempt/platform run关联。cohort区分正式计量、预热、多轮历史、故障/恢复、删除；多轮历史与预热实际产生的请求也必须计入相应事实，不能从后台“消失”。标签保存在测试清单，不擅自扩展普通事件契约或把原文塞入事件。需求榜中的重复频率是测试设定，不代表真实用户需求。

Basic QA性能原始文件仍按既有schema写入`docs/reviews/basic-qa-performance/<run_id>/`；联合验收报告通过共同campaign_id和证据索引引用，避免重复生成互相矛盾的requests/calls。A/B/C其他证据置于`docs/reviews/evidence/run/<新目录>/`，小型脱敏报告可提交。模型/外部服务未实跑项不得因共用采集器就标通过。

C另分三个执行范围：①聊天端到端，沿用S/R/F；②6/7原定规模数据的SQL/API基准，使用专用合成生成器，不为填满100万行而发起100万次模型调用；③相同聊天负载/种子/资源下，比较worker暂停且无后台查询与worker启用且固定后台查询的组合影响。组合比较保留授权、台账和观测，报告聊天延迟、连接池/资源、分析积压年龄与排空时间，不能关闭安全机制改善结果。35×2局部基准不能冒充足量聊天尾延迟或容量证据。

先补齐或复用发送/采集/报告工具，再跑A与P/S；真实配置E/S和B仅使用已批准的服务、案例和预算。R/F、后台规模、组合负载须在用户明确选择后启动，配置默认关闭，预算/时限达到即停并保留失败或中止记录。不得因为同一提示词包含全部阶段就自动跑满所有阶段。

## Risks / Trade-offs

- [案例近重复导致虚高分数] → 按语义家族划分，留出冻结，人工复核误差。
- [正式环境被当作方便的测试资源] → 自建空资源与随机凭据；DSN/端口/角色显式白名单，禁止15432/19132故障注入。
- [人类委托到期影响长任务] → 测试真实续期/暂停语义，不创建永久root令牌兜底。
- [外部服务不可用拖住整个项目] → 仅把对应场景记受阻，交付其他独立结果；不把业务代码提交与生产验收混为一谈。
- [验证再度无限扩张] → 范围只覆盖映射中的6/7现有要求；新增功能需独立提案。

## Migration Plan

当前不迁移、不启用生产。执行A时部署到自有空资源，从空库和包含合成存量的上一head分别升级；先创建受限角色，再应用迁移。回退停分析入口/worker，保留删除/到期清理；恢复时先重施墓碑和最小权限，不downgrade删除事实。B/C只增加测试输入与证据，不自动变更正式配置或数据。
