# 企业成员与访问权限

## Purpose

为多企业共享的 Agent 应用建立可独立管理的企业、部门、成员和角色作用域，明确企业管理与全局账号管理的职责，使同一用户加入多个企业时权限与个人业务数据仍可隔离和追溯。

## ADDED Requirements

### Requirement: 企业生命周期与有效成员

系统 SHALL 维护企业与成员的有效状态，仅有效用户在有效企业的有效成员身份可以发起企业业务操作；企业或成员停用后，后续请求和新的外部调用 MUST 被拒绝。

#### Scenario: 停用企业
- **WHEN** 平台管理员停用企业 A
- **THEN** A 的成员后续企业请求被拒绝，运行不再向外部发起新调用
- **AND** 企业 B 继续可用，A 的历史数据不因停用被删除

#### Scenario: 停用一个企业的成员
- **WHEN** 同一用户属于 A/B，仅 A 的成员身份被停用
- **THEN** 用户在 A 的操作被拒绝，在 B 的有效权限保持

### Requirement: 全局账号与企业成员职责分离

系统 SHALL 区分全局用户和企业成员；租户管理员仅管理本企业成员，不得修改其他企业成员、全局账号状态或密码、删除全局用户、枚举全局账号或未经授权关联其他用户。

#### Scenario: 企业管理员管理成员
- **WHEN** A 管理员编辑 A 成员的部门、角色或成员状态
- **THEN** 只改变 A 的成员属性，不影响同一用户在 B 的成员或全局登录身份

#### Scenario: 使用旧全局用户接口
- **WHEN** A 管理员通过旧用户接口尝试停用全局账号或重置其密码
- **THEN** 请求被拒绝，不能因接口兼容获得平台管理能力

#### Scenario: 同名账号关联
- **WHEN** 企业管理员创建的账号名已属于一个全局用户
- **THEN** 系统不自动关联或泄露该用户的其他企业信息，关联须经过有权主体的明确授权

### Requirement: 企业作用域的角色授权

系统 SHALL 按当前成员解析企业权限，角色分配和角色修改必须属于同一企业；平台权限与租户权限 MUST 分离，授权范围不得超过操作者允许授予的范围。

#### Scenario: 跨企业分配角色
- **WHEN** A 管理员向 A 成员分配 B 的角色
- **THEN** 系统拒绝，成员角色和审计对象保持原企业归属

#### Scenario: 自我提升为平台管理员
- **WHEN** A 管理员构造角色编辑或分配请求，加入平台权限
- **THEN** 请求被拒绝，内置模板不构成授权旁路

#### Scenario: 权限实时撤销
- **WHEN** 成员的工具或管理权限被撤销
- **THEN** 下一次对应请求或实际工具调用拒绝执行，已有页面菜单不影响此结果

### Requirement: 部门与成员业务数据同企业

系统 SHALL 保证部门父子关系、成员部门关联及成员偏好属于同一企业；同一用户的企业偏好 MUST 分开保存，公开行政区字典可以共享。

#### Scenario: 非法部门关联
- **WHEN** A 成员被赋予 B 部门或形成部门循环
- **THEN** 系统拒绝写入，保持现有合法关系

#### Scenario: 多企业关注城市
- **WHEN** 同一用户在 A/B 设置不同关注城市
- **THEN** 切换后各自回读对应偏好，不能混用其他企业配置

### Requirement: 管理资源搜索与计数隔离

系统 SHALL 在列表、搜索、分页、计数、详情和写操作中执行相同企业范围校验；对其他企业对象的访问 MUST 不泄露其存在性或成员信息。

#### Scenario: 搜索和分页
- **WHEN** A 管理员查询成员、角色、部门或审计并改变过滤和分页参数
- **THEN** 结果及总数只覆盖 A 的授权范围

#### Scenario: 猜测其他企业标识
- **WHEN** A 管理员提交 B 的成员、角色或部门 ID
- **THEN** 得到与不可访问对象不存在一致的响应，且不修改 B

### Requirement: 最后管理员与管理审计

系统 SHALL 保护企业最后一名有效管理员，除明确的平台企业停用流程外不得删除或撤销其管理员身份；企业管理写入与审计记录 MUST 保持一致，审计不得含凭据或密码。

#### Scenario: 移除最后管理员
- **WHEN** 管理请求使有效企业没有有效管理员
- **THEN** 系统拒绝并返回可读约束说明，原授权保持

#### Scenario: 管理与审计失败
- **WHEN** 企业成员/角色修改无法可靠保存相应审计
- **THEN** 修改不被报告为成功，也不留下无法追踪的权限变化

### Requirement: 两个前端共享企业上下文

系统 SHALL 在聊天与后台呈现当前企业和当前成员授权；无可用企业时显示明确状态，管理入口与数据必须按授权呈现，同时服务端持续验证权限。

#### Scenario: 普通成员登录后台
- **WHEN** 无管理权限的成员访问后台或直接管理地址
- **THEN** 界面显示授权范围或权限说明，管理 API 拒绝越权操作

#### Scenario: 企业管理界面
- **WHEN** 有权限的管理员通过键盘或指针创建/修改本企业部门和成员
- **THEN** 保存、校验、失败和空态有中文反馈，刷新后显示真实已保存结果
