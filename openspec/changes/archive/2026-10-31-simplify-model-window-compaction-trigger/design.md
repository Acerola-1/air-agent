# Design

## Context

动机和确认范围见 proposal.md。2026-10-26 只读核对基线为 `dev`、HEAD `5193d214d4bb5aed39db6349f5f975bd36f839a4`，仓库无 `.codegraph/`；工作区已有大量其他任务修改。本计划不能作为恢复旧 HEAD、重置工作区或重建历史运行环境的指令。

当前接线已经查明：

- `src/common/conversation_summarizer.py` 按用户消息切轮，`should_summarize_conversation` 用 `bool(watermark) or pending >= threshold`，首次后近似逐轮整理；`update_conversation_summary` 返回摘要、覆盖 ID 和状态，不删除 `messages`。
- `src/common/context_guard.py` 只读投影为摘要加未覆盖原文。基础问答 `src/common/business_graph/nodes.py:prepare_model`、数据分析 `src/data_analysis/nodes.py:prepare_model` 调用整理；工具循环直接返回 `call_model`，因此目前缺少循环中的整理入口。规划补充、answer 和 cleanup 还各有独立发送点。
- `src/common/model_budget.py:request_metrics` 当前取 `min(120000, window-output-safety)`；工具 schema 配额也经此计算。只改环境模板不能解除固定约束。
- `src/intelligent_tracing/guards.py:guarded_summarization` 给 lead、气象模型子任务、审查模型子任务装已有守卫摘要器。它依赖 SDK profile，当前安装 SDK 有 profile 时采用 85%/10%，没有时回落到 170K/6 条消息。`src/common/models.py` 当前未显式把部署窗口绑定到模型 profile，不能假设模型别名自动识别百万窗口。
- `src/common/business_graph/tool_wrappers.py` 已有大结果归档、JSON manifest 与非结构化全量分块摘要；多个单独较小的结果累计超限尚无统一治理。`src/common/text_reduction.py` 支持独立摘要窗口和分层合并，但有时限与批次配额。
- `frontend/components/chat/ChatPanel.tsx:Composer` 没有上限提示，后端两个显式图以 Python `len` 校验默认 8,000；`ContextMeter.tsx` 当前以 `input_budget_tokens` 作分母，需区分新水位和容量。当前 BFF 路径白名单没有配置读取入口。
- `langgraph.json` 的当前公开图只有三个。当前环境文件声明的模型已是 DeepSeek 别名，但仍配置 192K 窗口；该事实不证明真实服务商容量，不授权本计划切换模型或修改私有环境。

## Goals / Non-Goals

**Goals:** 将完整请求计量、窗口比例判断和有界整理组织为各发送点共用的能力；让触发与覆盖位置解耦；保留显式图与 DeepAgents 各自已有摘要实现；在真实模型子任务中保证同一策略语义。

**Non-Goals:** 重写摘要提示词、改成固定保留 20K 的 pi 摘要算法、删除 checkpoint 原文、另建聊天历史系统、增加模型来判断是否摘要、升级 SDK、重做溯源业务、改变知识检索/菜单/能力授权、承诺任意输入永远成功。用户未来可能换百万模型，本次只建立可扩展机制，不立即切换模型。

## Decisions

### 1. 决策背景与替代方案

用户认为现有摘要生成和持久化机制合适，问题在触发和配置；讨论 pi 只用于理解按容量触发及超窗恢复。pi 当前公开版本默认是窗口减 16,384 token，近期保留目标约 20K，不是默认 80%。本变更采用 80% 是用户最终确认的产品选择，不能在实现注释或交接中归因成 pi 原始算法。

拒绝继续使用“30K 新早期历史”或仅提高到另一绝对值；它们不能感知固定规则/工具开销，也不随窗口扩展。拒绝继续保留 120K 应用上限后再对窗口取 80%，二者会互相冲突。保留真实输入边界，因为取消人为上限不等于取消服务商物理限制。

### 2. 一个容量描述，两个主要压缩配置

沿用 `MODEL_MAX_CONTEXT_TOKENS`，新增有限小数 `CONVERSATION_SUMMARY_TRIGGER_RATIO`，默认 `0.8`，要求 `0 < ratio < 1`；普通同模型部署主要配置这两项。保留现有输出预留、安全余量、输入字符限制和独立摘要通道；“简化配置”不意味着删除这些不同职责的设置。

共享容量解析结果至少含：实际模型/通道标识、窗口 W、输出预留 O、安全余量 S、若明确存在则带服务商输入上限 I、计量方法和配置指纹。主模型使用明确部署 W；同一模型/同一通道的角色继承该描述。独立摘要模型使用既有 `SUMMARY_MODEL_CONTEXT_TOKENS` 等配置。注入的不同模型子任务从已绑定的受保护容量描述或可信 SDK profile 取得各自窗口；不同模型不冒用父图 W，不按名称猜容量，不从浏览器接受容量覆盖。现有同模型部署不强制新增每角色配置项；遇到未登记的不同模型则报可定位的配置缺失。

常规水位 `T = floor(W × ratio)`；有效输入边界 `H = min(W - O - S, I)`，无独立 I 时只取前项。要求 W/O/H 正且 S 非负。发送前 `input >= T` 进入常规整理，`input > H` 必须进入紧急容量治理；若 H 比 T 小，安全治理可以先于常规水位，页面仍显示两者的不同含义，不暗中把比例分母换成旧输入预算。

示例：W=192000、ratio=.8 时 T=153600；沿用 O=8192、S=4096 且无独立 I 时 H=179712。输入130000可以发；输入155000应先常规整理。W=1000000时T=800000，H根据真实该模型参数派生，绝不仍是120000。I只能表达真实通道限制，不能换个名字重建默认120K。

本次移除的是单次模型输入的旧应用上限，不删除溯源整次运行的成本预算、工具调用数、整理时限或安全配额；这些约束须以各自名称和原因报告，不能冒充上下文窗口。验收中“无120K/30K/170K隐藏限制”特指上下文输入与摘要触发路径。

### 3. 计量完整待发请求，不计完整存档账单

复用并收敛 `model_budget.py` 的输入拆分和工具 schema 处理，先确定实际工具定义再计量；只压缩说明时保留参数约束。`MODEL_TOOL_SCHEMA_BUDGET_PERCENT` 的目标基于派生 H，不继续引用已弃用的旧上限。

计入实际系统消息、用户系统规则、已加载 Skill、摘要、未覆盖原文、当前问题、调用参数、工具结果和请求封装。未发送的 artifact 原文不计入。新请求必须包含新增用户文本或工具结果再判断，不能只看上一次响应的数字；在多个并行子任务中分别计量。

可用专用 tokenizer 时优先；未知模型继续使用标明来源的多语言估算，不恢复字节上界。提供商实际输入可作为匹配请求的校准依据，但仅在模型/通道、系统规则、工具 schema、摘要覆盖及可见消息前缀指纹一致时才复用，再估算新增部分；不满足则重新估算。实现可以先复用现有全请求估算，不必新增复杂校准缓存；测试必须防止旧 usage、缓存子集、输出或累计账单覆盖新输入判断。

### 4. 显式图在发送前统一准备，更新可持久化

在共用层建立“构造投影 → 实际工具 schema → 计量 → 必要整理 → 重新投影/计量 → 最终检查”的准备入口，返回输入、指标以及需写回 state 的更新。节点接入时要合并这些更新；不能只改某个局部列表，导致下次仍恢复旧覆盖位置。

基础问答和数据分析初始准备可以继续组装业务提示，但历史整理最终必须位于每个发送点之前，覆盖 `call_model`、planning nudge、`answer_model`、cleanup 及从工具循环回来的请求。对于 cleanup 等临时派生提示，不得把派生消息 ID 写成主历史的覆盖 ID；可对其所引用历史做合法整理或治理派生资料，再检查实际发出的内容。

默认只把当前轮之前、早于最近三轮的完整轮次纳入常规摘要。水位低时未覆盖历史继续发送；不再因 `summary_covered_message_id` 存在就整理。成功后摘要覆盖到的历史才被投影移除，完整 `messages` 保留。摘要失败保持原水位和原文；若原输入仍安全可继续，否则进入明确失败路径。

近期三轮是目标。紧急治理时依次允许 keep_turns=2、1，将更早的已完成整轮纳入摘要；当前用户问题保留。每个扩围操作须有新的覆盖范围，禁止反复摘要同一前缀；以有限候选范围和前后输入变化检测终止。普通整理不要求每次都降到某个额外低水位，也不新增另一组固定压缩目标参数。相同消息/覆盖/工具指纹、无可整理内容或无容量改善时，不因仍在触发线附近无限重入。

当前轮工具结果累计过大时复用可靠归档、结构化 manifest/受限计算及非结构化全量分块整理，按调用组维持配对；不删用户问题，不清空工具参数假装合法，不裁断结果后声称已完整读取。原始载荷、归属、保留期和删除优先规则不变。

### 5. DeepAgents 保留原摘要器，替换容量/触发接线

`guarded_summarization` 接入同一容量解析和比例，显式传入动态 token 触发值或正确的模型 profile；不再依赖 SDK 是否认识网关别名。为避免 SDK 自己按不同输入范围判断，与显式图一致的完整请求检查应放在合适的模型 middleware 入口，并与摘要器共用同一准备结果，防止重复压缩。

覆盖 `intelligent_tracing/graph.py` 的 lead，`subagents.py` 的气象编译子任务和审查声明式子任务；须真实执行锁定 SDK 中的 child graph 验证，不以工厂构造成功为证据。站点/网格确定性子图保持零模型调用。通用适配器若被复用，只按本次三个公开图的可达路径修改，不扩散到历史废弃图。

SDK 现有 keep 策略不强行改成显式图的三轮，也不重写其摘要格式/归档；需要基于已解析窗口保留原有自适应语义，不能修改 trigger 后让 keep 仍落入隐藏绝对容量的错误分支。紧急整理同样只处理安全可分割内容，保留当前用户任务和合法工具闭合。继续使用 `GuardedSummarizationMiddleware._acreate_summary` 与已有观测包装，不旁路实时授权。

### 6. 一次模型级恢复，不重放运行

复用现有模型调用守卫，SDK `max_retries=0` 保持；对服务商明确上下文超限的结构化错误分类，例如 `context_length_exceeded`，并为当前网关实际返回形态建立适配测试。普通400、401/403、429、超时和网络结果不确定不得混入此恢复规则；本次不新增所有 length 终止自动重试。

首次模型容量错误后：保留首次尝试事实 → 强制进行有界安全整理 → 保存成功覆盖/状态 → 重新核权与重新计量 → 仅重新发送失败模型调用一次。第二次失败或整理失败/无进展则停止。恢复预算绑定原逻辑模型调用，不用每次摘要、节点重入或 SDK 内部调用重置。每个独立子任务有自己的逻辑调用预算，不共用主图的可变计数。

恢复不重新调用 `graph.invoke`，不重新提交用户问题，不重新启动已完成工具，不重置冻结请求或已受理能力快照，不创建新的顶层台账对象。摘要调用是独立 summarizer 观测；失败与恢复发送共享逻辑调用ID、拥有不同实际尝试ID及原因，未知 usage 为缺失。身份撤销、IAM不可用、取消、线程删除或上下文代次变化时及时停止外呼与迟到写入。

流式回答仅在尚无用户可见正文且能够确认未执行工具副作用时自动恢复；已有部分可见输出按现有 partial/aborted 终态处理，不再次发布重复正文。最终恢复失败是可解释的异常终点，不是正常历史增长的默认体验；不能向用户承诺任何输入在任何模型下都必然可消化。

### 7. 一个受信输入限制来源

保持 `MAX_INPUT_CHARS=8000` 默认值。定义字符为 Unicode 码点：前端按码点遍历，后端按同一已提交字符串的 Python `len`。页面在既有trim序列化之后，对实际将发送的字符串计数；后端对收到的文本原样计数，不另外用Python strip重新解释ECMAScript trim的空白字符集合。直接API提交的原始文本同样原样计数，不额外做Unicode合成或静默裁切。提供中文/英文/emoji/组合符/换行和边界空白样本；输入控件不依赖HTML `maxLength`的UTF-16计数。

在自定义 HTTP app 增加已认证、按 graph 校验业务资格的只读 `/chat/config?graph_id=...`，最小响应 `{max_input_chars, character_count_mode}`；经现有同源 BFF 显式加入 GET `/api/chat/config` 只读白名单，保留身份票据、企业与 context_version 核对。浏览器不读取私有 env，BFF不维护另一份上限常量，不向页面返回模型密钥/完整规则。响应 no-store；配置加载、失败、重试及旧结果隔离沿用 session/tenant/graph/epoch。

Composer展示计数/上限，超限禁发并保留完整草稿；按钮、表单和Enter共用提交检查，Shift+Enter、中文IME确认、粘贴和窄屏可用。读取失败前不提交，明确重试入口，不将草稿清空。后端校验尽可能置于模型/工具/业务路由执行之前，补齐溯源入口；真实超长文本拒绝必须配有合法文本的正向控制。该接口和页面只是长度体验，不构成授权依据。

### 8. 容量和状态的兼容扩展

继续使用已有 `context_metrics`、`context_status`，保留 `window_tokens`、`input_budget_tokens`、输入拆分及计量来源；`input_budget_tokens` 改为派生 H，不再是120K。增加可选 `summary_trigger_ratio`、`summary_trigger_tokens`，以及必要的整理原因/恢复阶段/逻辑调用关联字段；旧快照没有新字段时显示未知，不伪造已测量值。

页面主容量可继续以输入/H展示，tooltip明确列出W、T、输出预留及来源；状态报告实际保留轮数，不能仍写固定三轮。模型子任务状态单独关联角色/执行，不覆盖主模型胶囊。准备新请求时标记新指标/清除旧 latest_usage 的优先级，回答后才显示匹配调用的真实输入；历史快照标注最近一次，不与新部署配置混合。

若事件登记覆盖这些类型，同步源契约、Python/管理端/TS校验器、生成副本及样本；新增配置API同步实际OpenAPI及BFF契约测试。内部摘要、工具JSON和恢复草稿不进入正文，现有身份/线程/epoch隔离不回退。实施UI前读取设计技能、`DESIGN.md`、`UX-CONTRACT.md`、`frontend/AGENTS.md`和安装版Next.js文档，保持当前视觉。

### 9. 与旧 OpenSpec 的关系

当前主规格没有 `model-context-governance` 和 `chat-input-limits`，因此本次使用 ADDED，不对不存在的主规格写 MODIFIED。

旧 `mcp-tool-governance-context-guard` 中30K触发、120K应用预算及当期无限豁免的描述不再作为本次验收目标；`fix-langgraph-streaming-context-governance` 的成功覆盖、完整历史、未知token估算边界与摘要失败保留仍有效。本计划明确替代前述触发约定，不修改旧完成任务和验收报告。将来获授权归档时先处理同名能力的整合：若旧 change 先归档，则据届时主规格转换本增量为准确的 MODIFIED/ADDED，保留所有未被本次替代的要求；不得盲目并行归档覆盖主规格。

`upgrade-deepagents-0.7.28`、`add-intelligent-tracing-multiagent` 和当前溯源对话/数据证据 change 仍有开放验收，应保护其工作区改动及业务门禁。本次以当前锁兼容接线，不把它们的未完成项算作本次已通过。`revise-model-capacity-performance-testing` 是并发测试流程，不等于本次长上下文能力已验收，不能互相代替。

## Risks / Trade-offs

- 百万窗口和估算误差增加整理成本 → 保留独立摘要模型分块/分层能力，验证90秒等现有配额，报告批次数和真实时延；不通过扩大主窗口绕过摘要预算。
- 80%不是最优比例的实测结论 → 默认可配置，验证频率、输入量和事实保留，不附带调整为pi的16K预留策略。
- 一次巨大当前轮仍可能缺少安全可整理空间 → 先用已完成轮次和既有资料治理，再有界失败；不无限摘要、不破坏数据完整性。
- 状态投影与持久化脱节会反复整理或丢信息 → 检查成功/失败/取消/重启后的覆盖语义，真实checkpoint回读验证。
- 恢复导致授权/副作用/流式重复 → 每次发送守卫、独立观测、工具实际次数断言及可见正文终态控制；不做整图重试。
- 旧环境参数残留 → 启动只提示键名弃用，不打印环境内容；模板和说明给迁移步骤，不能在其他计算路径继续读取其作用值。

## Migration Plan

1. 实施前重新检查HEAD、工作区、实际模型/通道/容量和当前正式清单。已有192K等配置只作为声明，不证明服务商限制；不在本次计划中改成百万或承诺当前HY3仍在使用。
2. 引入比例及容量解析，停用两个旧参数的行为；旧键即使残留也忽略并提示。不要通过加载旧变量的默认值继续把120K藏在工具配额或页面里。
3. 依次接入显式图、DeepAgents主子入口、一次恢复、受信输入配置与页面契约，保留旧线程读取兼容；本次不需要删除或改写历史checkpoint。
