# Spec Delta

## Purpose

为运营提供轻量且可审计的反馈处理流程，记录已查看、正在处理和处理结果，避免用户点踩停留在不可跟踪列表。处理单独立于用户评价、回答版本和评测分数，其状态变化不能覆盖原反馈或被解释为答案已经解决问题。

## ADDED Requirements

### Requirement: 当前反馈列表与独立处理单
系统 SHALL 按当前有效评价列出反馈，另行保存待处理、处理中、已处理及重新打开记录；用户评价修订与运营处理修订分开。用户后来改为点赞或撤销不删除处理历史，也不自动认定问题已经解决。

#### Scenario: 关闭后用户又点踩
- **WHEN** 已处理的回答评价出现新的负面修订
- **THEN** 显示需要复核并可重新打开，满意率仅由当前用户评价计算，旧关闭不能掩盖新反馈

### Requirement: 写权限与正文权限分离
处理写入 SHALL 要求当前企业有效身份、运营读取权及独立的`agent:feedback:manage`。意见与处理说明正文另需`agent:content:read`；只读用户不能修改状态。新码未注册或未授予时失败关闭，不给root或企业管理员隐式旁路。

#### Scenario: 有运营只读无处理权限
- **WHEN** 运营只读成员直接调用处理写API
- **THEN** 返回403且状态、审计均无变更；明确获授者能执行同一合法操作作为正对照

### Requirement: 状态变更的幂等并发与审计
系统 SHALL 对每个处理操作验证唯一操作ID、载荷摘要、期望修订和当前企业上下文；同ID同载荷重放复用结果，异载荷或旧修订409。处理状态与审计原子提交，审计不含意见或处理说明原文。

#### Scenario: 并发关闭与事务失败
- **WHEN** 两运营人员使用相同修订提交不同处理结果，或审计写入失败
- **THEN** 至多一个完整成功；失败事务不留下半条状态，客户端保留草稿并可正确重试

### Requirement: 处理内容删除与安全呈现
系统 SHALL 对处理说明执行长度、正文访问和保留控制，不把自由文本写入普通日志或事件。源会话删除后立即禁读关联处理内容，晚到操作不能复活；未完成外部修复不能仅凭“已处理”宣称业务任务成功。

#### Scenario: 删除竞争与恶意说明
- **WHEN** 保存处理说明时会话被删除，或说明含HTML脚本
- **THEN** 删除优先且无可读派生正文；可读说明以安全文本呈现，不执行脚本
