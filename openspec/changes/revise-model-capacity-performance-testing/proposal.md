# Proposal

## Why

用户需要知道使用当前 HY3、DeepSeek 网关时，首段有效正文要等多久、系统在什么条件下能稳定承载多少并发。2026-10-24—25 两轮实际仅执行单并发 E/S，且存在知识检索缺失、质量断言偏差和错误归因，不能回答容量问题；现有规范虽定义 F 档，工具和交付流程尚未保证执行范围与目标一致。

## What Changes

- 整改规范、启动交接、报告模板和测试工具，建立显式运行计划与完成门禁；容量任务不能被 S 冒烟结果替代。
- 区分 U（当前网关/账号的上游模型）、P（受控依赖的平台）、E（真实完整产品）三个层次；HY3 与 `cn:deepseek-v4.1-flash` 分开出容量结论，不推断供应商全局极限。
- 首正文只统计紧扣问题、可公开且有实际信息量的文字；独立报告首次已核验结果、完整回答、模型首 token、浏览器可见与有效正文间隔，工具状态和空泛开场不计正文。
- 保留现有 F 的逐级探索、重复确认、开放到达、长稳、停止与排空要求；区分最高已验证档位、首个失败档位和预算下界，未找到边界不能宣称绝对最大值。
- 修正停止窗口、实际在途/吞吐测量、Q4 历史校验、真实数据质量断言和资源/usage 采集；保存失败及原始历史报告。

## Capabilities

### New Capabilities

- `model-capacity-evaluation`：拥有分层模型/产品性能评测的计划、发压、测量、门禁及可追溯容量报告行为；与 `agent-runtime-performance` 的应用运行时优化职责分开。

### Modified Capabilities

无。浏览器交互计时的产品契约由配套 change `improve-progressive-answer-output` 维护；本 change 消费该契约，不重复定义业务事件。

## Impact

- 实施范围：`docs/testing/` 的性能规范、模板与工具说明，两个性能交接提示词；`scripts/product_chat_perf/`、`scripts/unified_campaign/` 及对应测试。
- 产品容量首个基线沿用 Basic QA 固定 40 题；其他公开图的独立/混合容量必须有单独冻结 profile，不将单图结果外推为全产品容量。
- 依赖：现有台账、正式运行清单、受保护模型配置和配套输出 change 的语义单元；U 层和工具校准可先独立实施，输出优化后的正式 E 基线随后执行。
- 此次仅创建计划；不启动容器、模型请求、负载或部署，不修改 IAM/RAG 源码，不覆盖已有报告。正式长测的范围、阈值、时长和用量预算在执行计划中冻结，不沿用旧 90 分钟冒烟预算承诺完整 F。

## 当前实施上下文（2026-10-25）

用户已撤回配套正文 change `improve-progressive-answer-output`；当前无该生产端语义单元与新增 DOM 计时字段。性能采集协议和校准保持独立，U 层可继续验证；E/F 新判据集成及真实验收仍受阻。不得借性能实施重新引入已撤回正文行为，相关集成任务保持未完成。
