# Design

## Context

动机见 [proposal.md](proposal.md)。本次核查基线为 `dev@0b3c4bf` 加实际脏工作区，不能仅凭 HEAD 复现。最近两轮 manifest 均为 E/S、并发 1、`allow_load=false`；原始证据及复核见 `docs/reviews/basic-qa-performance/20261025-independent-result-review.md`。

已确认的入口与缺陷：

- `run_baseline.py` 仅执行 E/S，`load.py` 仅按 P/R 生成结果，尚无可信 U/F、E/F 的完整执行能力，不能改报告标签就算实现。
- `sender.py` 在创建线程前开始计时，识别 `final_output_delta`；浏览器首可见仍由前端独立采集。此前“首正文”主要发生在最终答案阶段。
- `load._stop_rule` 对 `client_complete_ms`（每请求耗时）排序构造 60 秒窗口，未使用真实结束时刻；现有测试也复用了该错误假设。
- Q4 评分将所有末轮无工具调用判错，真实 MCP 回答仍可能被 fixture 的固定“15时”检查；流完成与业务有效在汇总中未充分分开。
- 容器采样标称 3 秒，实测间隔中位数约 5.3 秒；CPU/内存限额模板与实际不一致，池/队列未采集，调用角色均为 other。需从源事实采集而非补写解释。

## Goals / Non-Goals

**Goals:** 在不改变产品行为的前提下，使测试工具真实执行冻结计划，输出可复查的首正文、最高达标并发、可持续到达率和限制来源；文档、工具能力与报告互相约束。

**Non-Goals:** 此 change 不改产品图输出、IAM/RAG 业务代码，不自动启动外部付费/长负载，不推断供应商总体容量，不把 Basic QA 容量推广至其他图。

## Decisions

### D1. 显式计划与能力预检先于发送

新增有版本的运行计划，声明 `objective`、所需 U/P/E 层、S/R/F 档、模型请求标识与实际响应核对、图/菜单/混合分布、候选并发、重复数、时长/样本、SLO/质量目标、到达策略、总时间/请求/Token 或费用上限、保留/回收策略及资源所有权。真实服务与负载继续双重显式启用。

工具公布可执行的层/档/指标能力；入口不支持计划时发送数必须为 0。计划、实际与偏离分别存储，最终只允许 `PASS/FAIL/BLOCKED/PARTIAL/LOWER_BOUND` 等有明确条件的结论；S 完成不能填充缺失 F。旧“90 分钟 + 每题一次”的交接只适用于 S，两个旧交接文档和 `unified-campaign-runner.md` 均增加显式范围标记和容量入口。

选择新增计划校验层并复用发送/采集模块，避免另起一套统计口径；拒绝只把旧 `load.py` 的 P/R 字符串替换成 E/F。

### D2. 三层分工与负载单位

- U：直接访问受保护配置中的当前网关，分别覆盖代表性的短/长上下文、普通正文流和带工具 schema 的规划调用。工具模式使用合成可重放参数/结果，不在该层执行实际业务 MCP。固定输出预算、推理模式及可共用参数；同样记录真实模型物理在途与重试。结论只属于网关、账号和时段。
- P：真实自有 IAM/PG/Redis/官方图/BFF，协议兼容且有明确延迟、长度、流块和失败规则的模型与 MCP；用于定位平台瓶颈，不作为模型排名。
- E：经同源 BFF 的完整产品路径，保留实时授权、持久化、观测、真实模型及正常知识/MCP 依赖。工具失败、权限错误和降级答复不能算对应数据题业务成功。

U 的并发单位是模型物理调用，E 的并发单位是独立在途问题；产品一次问题可能有多个模型尝试，因此同时报告二者，不能混用数字。上游限制未知时写未知，网关可达并不证明底层供应商身份。

首个 E 容量 profile 沿用 Basic QA 固定 40 题和 Q1–Q4 比例。支持其他图独立/混合 profile 的声明与代表场景输入，但必须冻结菜单、冻结请求/证据与比例；没有执行对应 profile 就不输出其容量。不得默默把主测改成廉价简单问候。

### D3. 容量搜索及可持续验证

沿用现有 F 门槛，不暗中缩成短批次：闭环探索 1/2/5/10/20/30，达失败或预算边界停；每档至少 5 分钟且覆盖固定负载。候选达标档按原规范重复 3 轮，每轮至少 10 分钟且每类至少发送 200 题；U 对应其冻结的上下文/工具模式类别。随后做冻结开放到达率档位、60 分钟稳定性、突发/恢复与适用故障隔离验证。停止条件触发后不强迫补失败样本。

没有已冻结绝对首正文/完成延迟及业务目标，只允许探索，不批准容量基线。保留原 P/E 成功率门禁；U 的成功率和协议正确性门禁在发送前冻结，不能将无有效正文或工具参数不合法当成功。用户关心的最大值表述为“在该资源/profile/SLO/配额下最高已验证 C 与 λ”，并列首个失败档。所有档通过只报至少达到，不伪造最大值；预算不足、只有闭环或未长稳时不得称可持续容量。

### D4. 首正文和吐字节奏统一语义

与输出 change 共用判据版本：`explanation` 必须对问题有信息增益，`finding` 必须有核验事实，`conclusion` 是完整结论；行动承诺为状态而非正文。服务端单元标签是候选事实，测试端仍以固定正反样本和语义抽查核对，不能由模型自标“有效”即通过。

计划中的核心指标：

- `client_first_answer_ms`：提交至首有效公开单元；注明包含线程创建与否。
- `client_first_verified_result_ms`：首个已核验结果，不适用题型单列原因。
- `client_complete_ms`、`confirmation_end_ms`：完整正文结束与台账确认分别计时。
- `max_answer_gap_ms`：相邻有效单元间的最长间隔；首段前等待、末段至完成/确认、失败后的右删失观察分开报告，不用心跳或插入标点重置。
- 模型 TTFT 分 reasoning/content/tool-call 首片类型，浏览器首可见按 DOM 绘制独立测量；Token/s 只有切分及时间来源可靠才报告，否则使用公开字符/s，reasoning/tool JSON 不算用户吐字。

引入性能证据 v2，保留旧 v1 目录和解释器。旧 first-answer 不能回填成新解释来源，跨版本比较必须列测量差异。公开明细只保留单元 ID、类型、长度、摘要和时间，正文在受控证据目录。

### D5. 真正持续发压、时间窗口和排空

调度器按整个测量段的单调时钟保存计划/实际提交、真实结束/截止时刻；各请求单独保存 elapsed。停止窗口依真实结束/截止时刻滑动，不按 elapsed 聚类。测试加入“相同耗时分散结束”和“不同耗时集中结束”的相反对照。

闭环保持目标在途并独立统计实测在途；Q4 的每个并行对话独立预置、验收，失败会话不继续测量。开放调度不因响应变慢而降低计划产生率，未发送、排队、连接限制与调度滞后必须落账。安全停止仅停止新增发送，在途逐个校准；客户端断流不能自动视作服务端已取消，未知结果不得换幂等键重发。

### D6. 依赖、质量与可比性预检

两模型使用各自干净资源及等价权限，冻结源码快照摘要而非仅 dirty 文件名、锁和镜像 digest、配额、prompt/schema、长度、模式、数据版本及冷热策略。正式 E 必须以有效正向请求证明知识/MCP 可用；缺失时该档 BLOCKED，U 仍可独立运行。

Q4 区分固定重放历史与真实生成历史两种 profile，不混合比较；固定用户历史不等于助手历史等价。所有必要历史成功并保留摘要才进入计量。受控/合成模式严格验证 gold；真实服务模式根据实际响应核对范围、数值、单位和答案，不能套 fixture 固定时刻。末轮是否需要新查询由案例决定，复用可信历史与日期/因子错用必须有相反测试。

分别报告技术完成、业务有效和质量合格完成。检查器修订另起版本重算，原 15/40 与 22/40 不覆盖；候选新分数不记为原模型实施成绩。

### D7. 证据、资源和可读交付

复用 bundle 并增加计划/实际阶段状态、调度时间序列、公开单元时序；模型尝试与请求 ID 独立。采集真实 CPU 配额/内存限额、实际采样间隔、BFF/IAM/应用/PG/Redis/压测端、模型在途和可得连接池/队列；缺指标就限制相应结论，不能默认填 0 或写“资源不是瓶颈”。

用量按测量/历史/预热/诊断/重试分 cohort；失败缺 usage 记覆盖缺口，未知费用不记零。每轮报告首先给出首正文/首结果/完成、最高达标 C/λ 与首失败档、瓶颈证据及预算限制。HTML/图表只是原始记录的视图，不能手填实测数字。

## Risks / Trade-offs

- [完整 F 可能消耗大量时间与 Token] → 运行前预算估算及硬上限；未完成报告 PARTIAL，不降低门槛冒充达标。
- [共享网关和实时 MCP 随时漂移] → 记录配额/响应模型、实际数据时间和相邻单并发对照，必要时只做范围受限的绝对报告。
- [解释更早但数据未更快] → 首正文、首结果、完整与静默间隔并列，检查质量和总消耗。
- [工具自测通过但无真实容量] → 单元校准、受控服务、官方隔离栈、真实模型及浏览器证据分级，不自动互换。

## Migration Plan

1. 先实施本 change 的计划校验、工具和文档及离线校准；不发压即验证旧 S 不能满足 F。
2. 输出 change 完成语义单元与计时契约后集成消费端；共享字段由一个集成者维护，避免相互覆盖。
3. 用自有临时资源做有限接线验证，待本次执行的范围/预算/目标具备后运行各模型的 U、E；P 按诊断需要执行，最终批准完整平台/产品容量时不得漏掉规范要求。
4. 新 bundle 与旧报告并存。回退工具版本不改历史成绩；收尾按计划保留待查看数据或只回收本任务资源，无默认正式部署。

## 当前实施上下文（2026-10-25）

用户已撤回配套正文 change `improve-progressive-answer-output`；当前无该生产端语义单元与新增 DOM 计时字段。性能采集协议和校准保持独立，U 层可继续验证；E/F 新判据集成及真实验收仍受阻。不得借性能实施重新引入已撤回正文行为，相关集成任务保持未完成。
