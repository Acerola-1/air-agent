# Air Agent 企业化总体路线图

日期：2026-10-12；状态更新2026-10-15。第1/2项已接管验收；第3/5项已同步规格并归档，用户豁免3最后的剪贴板文本实机抽查；真实企业MCP/生产门禁保留。下一项展开4，独立IAM并行规划/实施，不把全文理解成全部功能已经实现。

## 1. 已确认的产品边界

- 第一版服务多家企业，实施完整租户隔离。
- 企业共用一个外部业务/MCP 平台，各企业使用独立授权身份。首期不提供任意 MCP 地址接入市场。
- Codex 负责总体设计、OpenSpec 与独立验收；用户选择的实施 AI 通过 ZCode、Antigravity 或其他目标模式工具按单个 change 实施。先完成身份和事件基础，再展开后续详细计划。
- 企业管理员、运营、运维和普通成员使用中文界面；平台管理与企业管理分开。统计权限不自动授予原始对话读取、导出或凭据管理权限。
- 目标是用户行为可解释、成本可归因、问题可处理。正常生成答案、用户满意、业务任务解决是三类不同结果。

## 3. 总体架构与职责

```text
聊天 frontend               管理 admin/web
       |                          |
       +--> 统一身份与企业授权 admin/api
       |                          |
       +--> LangGraph API <-------+ 受授权的运行/对话接口
                 |
                 +--> 统一 MCP 平台（按企业/成员身份授权）
                 +--> 模型与辅助模型
                 +--> 完整资料归档
                 |
                 +--> Langfuse（观测、评分、链路）
                 +--> 业务事件（行为、运行结果）

业务 PostgreSQL --> 异步聚合 / 问题归类 --> 后台查询与处理
系统健康与基础设施监控 ----------------> 运维概览与告警
```

- 继续保留后台 API、Agent API 两个进程与现有两个前端；共享身份源及协议，不把后台数据库逻辑复制进聊天前端。
- 应用表用 Alembic 显式迁移；不修改 LangGraph 平台内部表结构作为业务统计捷径。归档的既有自动建表路径须与新迁移收敛，不可并发漂移。
- PostgreSQL 可共用实例；业务表、平台表及运维访问分清职责。应用自有租户表采用应用授权加数据库 RLS/约束；平台资源使用原生鉴权和资源过滤。
- Redis 用于既有运行基础和后续任务协调。先用事务 outbox、可重试后台任务与聚合表，不预设引入数仓或新的 Agent 框架。
- Langfuse 使用支持的 API，不直接操作其底层表。企业直接访问 Langfuse 时优先独立 project 和权限；共享 project 阶段只允许可信平台服务代理查询，不给企业用户共享控制台入口。
- 外部业务凭据由服务端按可信企业身份获取，只有引用进入业务记录；不进入提示词、消息、checkpoint、Trace、浏览器响应或错误日志。

## 4. 共享对象与身份契约

| 对象 | 标识与关系 | 统计/授权含义 |
|---|---|---|
| 租户 | `tenant_id` | 所有企业业务对象的隔离边界 |
| 用户 | `user_id` | 全局登录主体，允许加入多企业 |
| 成员 | `membership_id` + `tenant_id/user_id` | 部门、角色、成员状态和外部授权映射 |
| 会话 | `thread_id` + 可信租户/用户归属 | 多轮聊天，不等于一次运行 |
| 提问 | `request_id` + `user_message_id` | 一次已受理的逻辑提问；发送失败另记提交尝试 |
| 运行 | `run_id` + `request_id/attempt_index` | 重新生成/重试产生运行；内部工具重试不是新提问 |
| 回答 | `answer_id` + `message_id/run_id` | 反馈和复制关联具体回答版本 |
| 执行步骤 | `observation_id/tool_call_id` | 模型、节点、工具或 Skill 使用的一次执行 |
| 观测映射 | `trace_id` + `run_id` | 一次运行可有多个 Trace，显式保存映射并选主 Trace |
| 标准问题 | `cluster_id` + `tenant_id/classification_version` | 长期稳定意图；主题是另外的层级 |

通用维度包含图/主要业务功能/Skill/工具服务与工具/模型、发布版本、环境、可信时间、采集来源和数据完整性。运行可执行多个 Skill，主要功能与实际调用维度分开。

事件 schema 至少包括 `schema_version/event_id/event_type/occurred_at/received_at/source` 及相应身份和关联 ID。用户身份由服务端确认，不能采信客户端上报的租户或用户。成员部门与角色可记录事发时快照；历史按当时归属统计，不因人员调岗静默改写。

所有写入有幂等键；会话删除、租户停用、权限撤销、事件重复/晚到和任务重跑都有确定结果。保留期、原文删除与匿名聚合保留分开制定。新表不得默认把缺失租户归入某家企业。

## 5. 指标字典的首期口径

| 指标 | 定义与边界 |
|---|---|
| 请求量 | 已受理逻辑提问按 `request_id` 去重；内部 LLM/工具重试不增加请求数 |
| 活跃用户 | 租户时间窗口内发生有效提问的去重 `user_id`；WAU/MAU 不累加 DAU |
| 应用首内容耗时 | 浏览器提交至首个可见终答正文；同一单调时钟测量，不与服务器时钟相减 |
| 服务运行耗时 | 服务端受理至实际终态；与浏览器显示完成耗时分别记录 |
| 模型 TTFT | 某次模型调用开始至首 Token；不同于工具进度或应用首内容 |
| 技术完成率 | 正常完成运行 / 已结束运行；同时独列失败、超时、用户取消、等待人工处理，报表显示分母 |
| 用户停止率 | 发出停止意图的运行 / 已开始运行；停止阶段、触发来源及后端确认另列 |
| Token | 一次运行所有模型调用的实际输入/输出 usage；缓存和推理子集不重复相加；缺失、估算有标签 |
| 成本 | 价格版本/币种明确；模型成本与外部工具费用分开；未知价格/usage 不记零 |
| 满意率 | 当前有效正面反馈 / 当前有效评价；并列反馈覆盖率，不把未评价算正面 |
| 复制率 | 至少一次成功复制回答的可复制回答数 / 可复制回答数；与复制次数分开 |
| 任务解决率 | 仅对有明确反馈、业务结果或评测证据的样本计算，同时展示证据覆盖率 |
| 工具失败率 | 技术失败、业务无结果、参数校验、权限拒绝、取消分开；重试尝试和逻辑调用分开 |
| 延迟分位数 | 用明细或可合并分布计算 P50/P95/P99，不平均小时/每日 P95 |
| 热门问题 | 原子意图次数与独立用户并列；问题数、消息数、请求数是不同分母 |

明确使用 Asia/Shanghai 的业务日与半开区间 `[start,end)`；数据库事实时间用 UTC。当天、最近 7 个业务日、最近 30 个业务日与滚动 168 小时必须分别命名。报表显示数据截止时间、同步延迟、覆盖率和口径版本。

## 6. 前台补齐与后台页面范围

前台依次增加企业上下文、真实运行终态与停止确认、点赞/点踩/原因/撤销、复制成功采集、重试/重新生成版本关联、授权 Skill/工具能力选择、可选已解决反馈。导航取消、等待中停止、输出中停止及连接丢失分别记录；不推断用户为什么离开。

后台复用现有壳与用户/RBAC/审计页面，逐步增加：

1. 总览：请求、用户、延迟、结果、Token/成本、数据覆盖率。
2. 用户与组织：企业成员/部门/角色、用量、活跃与成本。
3. 对话与反馈：按权限检索、回答版本、运行时间线和授权 Trace 入口。
4. 能力与性能：Graph、Skill、MCP Server/Tool 的使用、重试、降级和异常。
5. 模型与成本：实际 usage、定价、成本归因、预算和高成本运行。
6. 需求洞察：标准问题/主题、增长、独立用户、未归类与未解决证据。
7. 质量工作台：反馈、抽检、Scores、数据集与回归对比。
8. 运维与治理：健康、告警、审计、问题分派、复评关闭和配置发布。

每页有加载、空态、错误、数据未采集、权限拒绝和分页；不展示伪造示例 KPI 作为真实数据。租户切换清除旧数据、请求和可见缓存；长列表与明细回读有界。视觉延续两个前端现有设计，不在身份阶段全面重做导航。

## 7. 热门问题与诉求分析设计

问题事件异步进入脱敏/必要的多轮指代补全/原子问题拆分，再做向量候选检索、动作与实体语义校验、歧义复核；低置信度进入未归类池。稳定 `cluster_id` 支撑 SQL 时间统计；LLM 只辅助消歧、命名与摘要。

原文与标准化问题分存，保存来源消息、拆分索引、模型/提示/分类版本与置信度。聚类、检索、代表样本和报表都在授权租户范围内处理；不向其他企业展示样本或汇总。默认不做跨企业语义归并。

针对空气质量业务先评测实时查询/历史趋势/原因分析/治理建议等不同意图，保留城市、日期、因子和权限语义。主题相似不代表标准问题相同。Skill 路由仅可提供候选标签，不直接当热门问题分类。

先用脱敏标注样本校准误合并率、归类质量与覆盖率，再选择具体 embedding、阈值与聚类算法。已有向量模型可以复用，但不能假定 PostgreSQL 已安装 pgvector。算法升级、合并/拆分和历史重算有版本及审计。LLM 报告引用程序计算的统计和授权样例，原因判断标记为待验证。

## 9. AI 交接与完成条件

每个实施包包含 proposal/design/specs/tasks、文件衔接、已知基线、验收矩阵与交接提示。实施 AI 读包后直接 apply 单个 change，按任务推进、测试与修复；Codex 独立检查 diff 和真实行为。任务勾选不替代证据，实施完成不等于独立验收通过。

用户将以匿名方式交付多个 Flash 模型的实现，再由 Codex 盲评后揭晓。评估方法见 [匿名评估协议](flash-blind-evaluation.md)：不同 change 的难度与外部条件分开记录，实现正确性、稳定性、应用运行性能和实施效率不能混为一个速度排名。

阶段状态统一：`待设计 → 可实施 → 实施中 → 待独立验收 → 已验收 → 已同步归档`。遇到外部契约或凭据缺失，记录具体阻塞、完成不依赖它的任务，保留相关验收未完成。不可用模拟测试冒充真实平台授权。

每次完成交付需要：

- 相关正向、跨租户/跨用户/撤销、并发及失败路径测试；全量检查对照基线。
- API 与真实 PostgreSQL 的联调，前台/后台实际浏览器验证，MCP/模型按所涉范围实际验收。
- 迁移前备份、dry-run/冲突报告、幂等复跑、必要的恢复演练。
- `.env.example`/运行说明、版本与依赖影响；凭据和原始个人信息不进版本控制或证据。
- 对应 specs/tasks 与实现一致，独立验收后再同步主规格并归档；不顺便实施下一 change。
