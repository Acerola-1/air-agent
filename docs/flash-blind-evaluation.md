# 实施 AI 匿名评估协议

日期：2026-10-12。用户希望先隐藏 Flash 模型身份，让不同模型实施若干 change，由 Codex 独立评估后揭晓，以选择主要实施模型。本文固定证据与判定方法，不预先评价任何模型。

## 1. 匿名与可比性

- 用户使用匿名编号（例如 A/B/C 或运行 01/02/03）交付实现，评审前不提供模型名、供应商或模型宣传性能。
- Codex 先根据实现、可复跑测试和真实行为记录结论，再由用户揭晓。评审不通过代码风格猜模型身份。
- 每轮记录 change、起始代码与规划版本、实现差异、环境/依赖、实测范围、已知基线与缺失外部条件。
- 不同 change 的复杂度、外部依赖与改动面积不同，不能用完成耗时、失败数量或一个总分直接宣布模型排名。
- 最强对比是同一冻结 change/基线/验收输入下的独立实现；用户暂采用不同 change 时，以各自契约达成度和共同回归题比较，结论注明“跨任务观察”。
- 多个候选实现必须各用独立 checkout/worktree/测试数据库；不得同时修改当前同一目录或共享可变验收数据。提交/分支由用户实际流程授权，评估不自动改变代码或合并。

## 2. 每轮交付输入

| 项目 | 内容 |
|---|---|
| 运行标识 | 用户匿名编号；未提供则“本轮实现”，不编造模型信息 |
| 起点 | 代码基线 hash、OpenSpec 文件版本、起始已知失败 |
| 交付范围 | diff/提交范围、任务状态、发生的契约调整及理由 |
| 验证 | 命令、环境、输出摘要、spec 场景到测试与真实证据的对应表 |
| 外部条件 | 实际 PG/模型/MCP/浏览器可用性、缺少资料及阻塞任务 |
| 效率 | 若执行工具提供，则记录实际工作时间、工具次数、重跑/修复次数、Token；无数据写“未采集” |

不把 Git 提交时间差当实施耗时，不把作者自述的通过当复验，不从代码量推测 Token 或成本。报告与截图不包含秘密、原始 cookie、密码、敏感对话或模型身份。

## 3. 先做通过门槛

出现下列任一情况，本轮不可直接作为主要实施模型的正面证据；先标出具体代码、复现输入和影响，再修复：

- 跨租户/用户读写、主体伪造、凭据泄漏、生产授权旁路。
- 迁移丢数据、错误合并身份或不可恢复的破坏性操作。
- 未实现要求却勾选完成、模拟结果冒充实测、测试断言失效或删除/跳过测试掩盖回归。
- 重要用户流程无法实际完成，或依赖可用时仍没有合理实测。

外部凭据确实缺失且实现者安全拒绝、清楚保留任务时，属于明确阻塞，不等同虚报，也不能算该真实能力已经通过。

## 4. 实现效果评分

先过门槛，再按同一评分表记录 0–满分及证据；评分帮助解释取舍，不替代必需场景。

| 维度 | 权重 | 判定依据 |
|---|---:|---|
| 契约正确性与业务可用 | 30 | spec/任务真实实现，正向、失败、并发、迁移行为符合设计 |
| 权限和数据边界 | 25 | 授权位置正确、跨租户覆盖、身份/缓存/数据库一致，无凭据暴露 |
| 测试与验证可信度 | 20 | 独立可复跑、断言有效、真实与模拟区分、基线回归说明准确 |
| 可维护性与项目契合 | 15 | 复用既有模块、职责明确、依赖克制、错误/配置/文档一致 |
| 范围控制与交付完整 | 10 | 不无故扩大范围、交接清楚、无遗留 TODO 冒充完成 |

通用能力与本轮专题分别记录。例如身份 change 的 RLS、会话、MCP 授权，热门问题 change 的归类效果、统计口径与重算，分别需要专题验收，不能把它们的测试数量直接比较。

## 5. 稳定性、运行性能与实施效率分开

**实现稳定性：** 独立验收发现的问题严重性、首次通过的关键场景比例、修复轮数、重复运行是否一致、修改是否引入旁路和新回归。单次 change 只能说明本轮表现；主要模型选择需要多个样本。

**应用运行性能：** 在一致的版本、数据、资源、并发和模型/MCP 条件下复测；固定预热与样本量后比较延迟分布、错误率、数据库查询、资源消耗和实际模型 usage。外部服务延迟与本地新增开销分开，性能不能靠功能失效或删安全校验换取。未实测时写未知。

**AI 实施效率：** 有来源的用时/Token/工具调用与修复次数。自动等待、外部服务不可用与真正实现时间区分；不以快但未经验证的实现压过正确可靠的交付。

在后续实现具备对应接口后，保留共同回归题：合法登录与本人资源、A/B/同用户双成员隔离、权限撤销、停止/切换/恢复、归档与完整数据、工具失败/重试、普通/专家查询容量。每轮只运行适用题，说明环境与不适用原因。

## 6. Codex 盲评步骤与输出

1. 固定匿名输入与待评 diff，核对 AGENTS、规划、基线和实际运行配置；不读取用于揭晓模型身份的私有映射。
2. 检查接口、数据迁移、可信身份与权限调用路径，提出有复现依据的发现。
3. 运行受影响测试、负向/并发场景和本轮真实验收；必要时增补能够暴露问题的测试，不能仅镜像实现。
4. 给出“通过/需修复/受外部条件阻塞”、关键问题、五维分数与各维证据、运行性能与实施效率单独记录。
5. 在 `docs/reviews/flash-blind-<匿名编号>-<change>.md` 保留结论；用户揭晓后才关联模型，修复后复验，不能事后迎合身份改分。

未完成真实验收时允许结论是“代码部分可接受，某项外部条件待验证”，不能称完整通过。后续主力建议基于多轮一致表现和实际业务适配，明确样本数量与跨任务限制。

## 7. 后续揭晓与选择

用户可以让各模型各做一个不同 change，再逐轮返回盲评。初期先积累匿名结果；若两个候选表现接近，选择同一冻结的小范围修复/增强题做补充对比，而非重写全工程。最终分别给出主力实现、适合的任务类型、需要更强审查的弱点；不会凭一次速度宣称普遍最优。
