# Agent 性能与并发压力测试流程

版本：`AGENT-CONCURRENCY-v1.0`；修订：2026-10-26。适用于本机 macOS，默认测 `basic-qa` 的真实模型端到端并发。执行器要求见第 7 节。

**每轮只回答一个主问题：在记录的机器、部署、模型、题目和用户体验标准下，能同时处理多少个独立问答任务？**

执行顺序：**冻结本轮条件 → 正常问答检查与预热 → 持续阶梯升压 → 相邻边界复测 → 报告与归档。**

## 1. 先选范围，默认直接测真实产品

默认使用浏览器实际调用的 BFF → 真实 SSO/IAM → 台账 → LangGraph → 当前模型、知识/MCP → 完整正文与终态。保持当前部署功能、资源配额、超时、重试和 Langfuse 配置；同一轮中不调参。浏览器渲染另测，不能用接口时间代替。

每轮固定一个模型，更换模型时另建轮次。一个问题可能多次调用模型，**产品并发问题数不等于上游物理模型并发数**。

默认工作负载 `BQA-Q12-v1`：`BQA-001`–`005` 与 `BQA-011`–`015`，Q1/Q2 各半、有限题库确定性轮转、每问新线程、保持正常授权与工具选择。另选全 40 题、其他图或多用户画像时另建 profile，不能把这 10 题的结果说成全部产品容量。Q4 须每个并发线程独立建立并确认历史。

模拟模型的平台测试和直连网关的上游测试作为独立诊断，按需选择。

执行任务需声明可用环境、账号/企业、问题集、预算及保留策略。授权范围不足时先完成计划，再取得所需授权；已有授权范围内直接执行。正式环境仅通过正常问答产生会话、台账和观测，保留现有账号与业务数据。自有临时资源按计划回收，共享资源按其运行规范管理。

## 2. 每次开跑只需冻结一份计划

复制 [plan.template.json](templates/plan.template.json)，填写实际值，保存到新轮目录的 `plan.json`。计划由产品负载适配器读取，并在发送前完成字段和预算校验。

必须填写：

- `run_id`、标准版本、实际入口、模型请求名及可得回显名、图/题库/比例、独立线程和账号企业分布。
- 当前分支/HEAD、与本轮相关的脏源码摘要、锁/镜像/构建来源。
- 机器内存/CPU、实际组件及配额、发压器位置、后台活动、观测与冷热状态。上限、真实占用、可回收缓存分别记录；未知填 null。
- 成功与时延门槛、档位/时长、样本要求、请求截止时间、停止/排空策略、总时间和逻辑问题上限；物理调用/Token/费用可得则记录。只有限逻辑问题数不能宣称已限制全部物理 Token。
- 本轮资源保护参数及其依据、账号授权范围、数据保留策略。模板中的建议值是起点，不是行业强制标准或付费授权。

计划未填写必要预算或真实调用未授权时不发压。受保护口令/会话只记录文件或环境变量引用，不写入计划值。开始后标准和配置冻结；调整条件必须停止本轮并建新轮，不改阈值“洗成通过”。

## 3. 正常运行检查与少量预热

1. 检查本轮依赖的服务状态，复用健康服务，按 [正式运行清单](../CURRENT-RUNTIME.md) 和 [本机启动说明](../../deployment/SEPARATED_LOCAL.md) 恢复缺失的必要服务。核对实际配置与本轮计划一致。
2. 先开始独立资源监测，覆盖发压器导入和初始化；恢复服务时也要有启动保护。确认采集能读到实际资源，停止动作有明确对象且能执行。
3. 正常 SSO 登录，核对账号/企业，分别完成至少 1 道 Q1、1 道 Q2：新线程受理、流式非空正文、正常结束、可信台账关联和必要工具结果。验证不是 HTTP 200 就放行。TCP connect 不单独证明桥接健康，要有实际应用请求。
4. 做 2–5 个顺序预热请求，记录并计入总预算，排除出正式分位数。复用刚才成功的预检请求时注明，不重复发送凑数。确认 Langfuse 的自然 trace 能入库、用户/会话匹配，再开始低并发。

服务健康、代表题成功且资源监督可用后，从 C1 开始。记录启动前的资源快照；本轮资源预算须明确统计口径、停止阈值和执行方式。监测停止预算与操作系统硬配额分别记录。

若机器明显卡顿、存在严重且持续的内存压力，或正常问答无法完成，停止并报告 `ENVIRONMENT_BLOCKED`，记录故障和资源证据，修复运行条件后另建轮次。该状态表示测试环境未就绪。

## 4. 闭环阶梯升压：完成一个，立即补一个

一个虚拟用户串行执行一个完整问答；一个在途任务从线程创建前开始，到流结束及台账确认/截止处理结束。每个并行任务独立线程和幂等键；同一账号的会话可以模拟多个独立任务，但报告必须注明“单账号、多线程”，不能声称已测多账号公平性。

默认目标 C：**1 → 2 → 5 → 10 → 15 → 20**；后续每次 +5，直到未达标、保护停止或预算到限。不要一口气创建全部任务。切档以每秒至多增加 1 个虚拟用户缓慢达到目标，保留实际爬坡耗时；每档停止后先排空，再开始下一档，避免重复请求和阶段串账。

每档达到目标用户数后，先观察 60 秒，排除为稳定准备段；随后持续测量 **300 秒**。请求慢时仍持续保持目标任务槽位，不是发一批再 sleep。所有请求的发送阶段在发送时固定，跨窗口结束不改归属。

- 按每秒采样记录目标用户数、实际端到端在途、可得平台运行/排队数。若新发尚有预算且没有停止意图，一个任务结束后应立即补发；记录补发延迟。
- 端到端在途达到目标 90% 以上的采样须占测量段至少 90%。达不到时定位受理失败、快速错误、发压器调度还是服务排队；未证明负载达到，不能直接判该档通过。
- 标准阶段至少 20 个测量段发送样本，Q1/Q2 各至少 5 个。不足时最多延长一次 300 秒；仍不足记 `LOW_SAMPLE`，不强压补量或报告容量已确认。样本少须展示分母，不作成功率置信保证。
- 单请求截止默认 Q1 60 秒、Q2 120 秒，自线程创建前起算；技术流完成、台账完成、晚到、业务中止、超时和未知终态分别统计。截止与安全停止都不能触发盲目重发。

C1 已不符合业务 SLO 时，报告“单并发已未达标”及具体失败项；可以记录技术能力作诊断，但不把更高的技术完成档作为达标容量。尚无明确上界时，预算余量足够才继续升压，不预设 C10 或 C20 是终点。

## 5. 每档判定和边界确认

默认用户体验门槛：按时完整、非空且可信关联的完成率 **≥99%**；接口首正文 **P95≤45 秒**；完整回答 **P95≤60 秒**。这些是本流程的默认目标；更换目标须在本轮发送前冻结。按 overall、Q1、Q2 分别检查，不用四舍五入后的成功率作判断。

业务有效须核对必要工具/检索是否成功、回答范围和基本语义是否有效。事实正确性按真实工具结果/独立 oracle 抽查，记录抽查数量和 PASS/FAIL/UNKNOWN；模板规则匹配不等于事实正确。缺少 oracle 时，结论限定为技术/体验容量，并注明事实质量的验证范围。已确认业务无效不得算合格成功。

探索档位全部满足 SLO、实际负载和监测要求才记通过。吞吐平台期用于识别饱和线索，SLO 用于判定体验是否达标；两者分别记录。

找到最后通过 L 和未达标 H 后，恢复低负载确认无遗留积压，再测整数中点，缩小到相邻档位。最高候选 N 与 N+1 各做 **2 轮独立复测**；N 每轮稳定准备 60 秒后计量至少 600 秒，至少 30 个发送样本且两类各≥10，最多延长一次 600 秒。N+1 沿用探索时长和样本，已经明确过载可保护性早停并标原因。各轮单独给结果，不平均 P95。

- N 两轮都达标、N+1 两轮均有可复现 SLO 失败、恢复正常且证据完整：写“本配置、该负载及本轮验证时长下，最大确认并发 N”。注明每轮实际时长和样本。
- N+1 是宿主安全停止或发压器先饱和：只能写“已确认至少 N，上界受本机保护/测量能力限制”，不能硬称产品最大值。
- 更高档未测或预算截断：报告已证实下界。边界结果相互矛盾、样本不足、未知终态未核对：`PARTIAL`，不挑最好的一轮。

本标准默认结论只覆盖本轮验证时长。若另有长期或生产验收目标，在同一份计划中显式增加扩展：开放到达率各档至少 15 分钟并记录未发量；候选并发至少 60 分钟长稳；突发后恢复和获准故障场景；浏览器实际可见时间。扩展须事前冻结单独预算和判据，按实际结果独立验收。报告分别列出已执行的扩展及其结果。

## 6. 指标与停止：围绕用户问题，不围绕工具首包

每个问题至少保存：唯一 run/阶段/档位/sequence/case 标识、thread/submission/attempt/run 关联、计划/实际发送/结束/截止的同源时间、发送阶段、正文是否非空、业务结果、错误分类、首正文和完整时延。公开明细不保存问题/答案正文、Cookie 或内部推理。

- **首正文**：提交前至本轮第一段有回答价值的公开文字；排除工具事件、心跳、空串、历史消息和推理。使用 legacy 解析时标记 `legacy`，并通过抽查记录正文判定的准确性；具有语义单元标签时记录标签版本和校验方式。
- **完整回答**：提交前至流正常结束；台账确认另记，确认失败不能算成功。
- **成功率**：测量段发送 cohort 的成功数/全部逻辑发送数。受理 503、429、工具保护中止、超时、空答案和未知结果保留在分母。未发任务单列，不计成成功；保留原始分数与计数。
- **成功吞吐**：计量墙钟窗口内可信成功结束的问题数/实际窗口秒数。与发送 cohort 分开标注，不把发送数/秒当完成吞吐，跨边界明细可重算，不混入预热完成。
- 首正文分位数标有正文/应有正文样本覆盖；完整分位数标完成样本数，失败/截止不以 0ms 补入。不能只报成功分位数而隐藏失败率。模型 TTFT、模型 Token/s、浏览器首屏分别列，未采集填 null。

独立采集宿主、发压器和可得组件资源（目标每 2 秒，保存实际间隔）；区分资源限额与实测、guest usage 与缓存、宿主进程和 VM，避免双计。连接池、队列、上游物理并发拿不到就标未采集。

发送前按计划配置并校准资源保护。发压器 RSS 停止阈值可从 512MiB 起评估；宿主交换、压缩增长和服务预算分别记录阶段基线、阈值及依据。验证超限和采集失败均能停止新增负载，停止范围限于本任务拥有的对象。

以下发生即停止新增发送：

- 资源监督触发、OOM、服务退出或明显不可用；采集缺失使安全监测失效；发压器无法稳定达到目标。
- 任意身份隔离/越权/重复执行问题；任意 60 秒真实结束/截止窗口内至少 20 个请求中失败比例 >10%。按结束/截止时间计窗，不按请求耗时排序。连续明显故障无需等满窗口。
- 本轮总墙钟、逻辑问题或可执行物理 Token/费用上限到达；剩余额度不足下个完整阶段时不开始下一阶段。

常规停止先停新发并排空，核对已受理运行；客户端断流不等于服务端取消，不换幂等键重发未知提交。资源紧急停止可由监督器终止自有发压进程组，随后用台账核对未知运行。恢复时区分常驻共享服务与本轮启动项；只按启动归属和正式规范优雅收尾，不 prune、不删卷、不终止无关服务。

## 7. 执行工具

首选 **Locust + 项目自己的薄适配器**，用成熟框架调度用户、记录统计；薄适配器只负责本产品 SSO 会话、线程创建、SSE 首正文/完成、可信确认、预算与资源停止接线。可以复用现有发送器规则，但必须校准其客户端与 Locust 的协作，不能因同步阻塞导致实际只有一路并发。

**执行器状态：Locust 产品适配器待实现与验收。** 实现要求和验收清单见 [执行器说明](executor-handoff.md)。验收通过后记录工具版本和运行命令，每轮复用。

可复用的检查与采集工具：

- `deployment/run_separated_local.py status/start`：现有正式应用检查/恢复；不含所有依赖自动恢复，必须先读部署说明。
- `scripts.product_chat_perf.local_resources --out <新文件>`：只读资源盘点。
- `local_supervisor` / `startup_guard`：资源监督和启动保护；按计划配置阈值并核对服务统计口径。

## 8. 保存结果，每轮都能重新统计

新建 `docs/performance/YYYYMMDD-HHMMSS-模型-目的/`，时间使用 Asia/Shanghai。保存冻结的 `standard.md`（本文件副本，复制后修正相对链接）、`plan.json`、实际 `conditions.json`、逐请求 `requests.jsonl`、资源 `resources.jsonl`、`stages.json`、`results.json`、`report.md` 和脱敏证据索引。模板见 [结果结构](templates/results.template.json) 和 [报告](templates/report.template.md)。

模板的 null 是未采集/未执行，不是零；实际未发送可以明确记 0。目录创建、执行起止、标准修订时间分别记录。凭据、受控正文和原始私有观测只在 `.local/<run_id>-private/`，不提交。

每档给出目标/实际并发、发送/按时成功/失败/未知、首正文和完整 P50/P95及覆盖、成功吞吐、资源峰值、停止原因；探索、候选复测、恢复各阶段独立列。Langfuse 自然采集覆盖、入库延迟、身份关联、模型请求/回显名、可得 usage/费用单列；补录覆盖不能冒充自然采集，trace 漏采不自动变成业务失败，但使依赖 trace 的瓶颈结论受限。价格未知记未知。

报告首句直接写并发 N 或已确认下界，再写相邻档失败和限制。更新 [倒序索引](README.md) 与 [index.json](index.json)，保留全部阶段和失败记录，每轮使用独立目录。

后续回归先复用上一轮确认档和邻档；需要重新找最大值才重新全阶梯。比较须匹配模型/配额、机器与配置、入口、题库比例、SLO、计时和观测口径；不平均不同轮次 P95，不把后台干扰变化写成代码加速。

## 9. 方法来源

参考资料访问日期：2026-10-26。档位、时长、样本数和 SLO 按本流程及本轮计划执行。

- [Databricks：Agent 负载测试](https://docs.databricks.com/aws/en/agents/custom-agents/load-test-agent-app)：支持 LangGraph；健康检查、预热、阶梯加压、饱和分析；真实端到端测试可跳过模型模拟，平台模拟结果与真实 Agent 结果分开。
- [Locust：首个测试](https://docs.locust.io/en/stable/quickstart.html)：用并发用户制造持续请求，观察吞吐与时延拐点。
- [k6：固定并发用户](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-vus/) 与 [阈值](https://grafana.com/docs/k6/latest/using-k6/thresholds/)：固定并发重复任务，按自身 SLO 判断；不是单批发完等待。
- [k6：发压器资源](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)：同时检查被测系统和发压器，避免把发压器瓶颈算成产品容量。
- [NVIDIA：LLM 推理指标](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)：区分首 Token、完整时延与吞吐；应用首正文还包含规划和工具等待，不能用单次模型 TTFT 替代。
