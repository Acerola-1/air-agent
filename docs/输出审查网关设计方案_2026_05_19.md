# 输出审查网关设计方案

## 一、背景与目标

当前智能体链路已经具备身份识别、意图识别、权限校验、受控工具调用、LLM 生成等能力，但最终回复仍然主要依赖提示词约束。对于大气环保业务，最终输出可能包含企业精确监测数据、内部执法线索、污染归因定责、实时预警信息、个人信息、系统实现信息、单位错误和不当健康建议。这些内容如果仅靠模型自觉遵守，稳定性不足。

建议增加一个“输出审查网关”，作为最终返回用户前的强制审查层：

```text
用户请求
  ↓
身份认证 / 租户识别
  ↓
意图识别
  ↓
权限策略判断
  ↓
受控检索 / 受控工具调用
  ↓
LLM 生成
  ↓
输出 DLP / 脱敏 / 合规审查
  ↓
返回用户
  ↓
审计日志
```

输出审查网关的目标不是替代前置权限，而是补齐最后一道强制防线：

- **防泄露**：避免企业敏感数据、内部执法信息、系统信息、个人信息进入最终回答。
- **防误导**：拦截单位错误、污染归因过度定责、绝对化健康建议。
- **可追责**：记录输入、输出风险、命中规则、处理动作、用户身份和租户上下文。
- **可演进**：规则可配置、可灰度、可审计，不把所有逻辑写死在提示词中。

## 二、总体设计原则

1. **前置最小化，后置强制审查**

    受控检索和受控工具调用阶段仍然要做权限过滤，尽量不把无权限数据交给模型。输出审查网关只作为最后兜底，不能承担全部数据隔离责任。

2. **规则优先，模型辅助**

    正则、词典、结构化字段、单位规则、权限矩阵等确定性规则优先执行。只有污染归因、执法语义、健康建议等需要语义判断的场景，才调用轻量 LLM 审查器。

3. **审查结果结构化**

    审查器必须输出结构化结果，例如 `allow`、`mask`、`rewrite`、`regenerate`、`block`、`escalate`，不能只返回自然语言判断。

4. **按身份和租户做差异化策略**

    同一段内容对外部公众、企业用户、属地监管人员、平台管理员的处理方式不同。输出审查网关必须读取用户角色、租户、数据范围、登录用户 ID 和会话来源。

5. **审计日志不记录原始敏感值**

    审计日志应记录命中规则、风险类型、处理动作、脱敏摘要和 hash，不应把手机号、token、企业小时值等敏感原文完整落库。

## 三、推荐技术栈

### 1. 网关实现层

建议在当前 DeepAgents / LangGraph 项目中新增 `OutputComplianceMiddleware`：

- 放在 `src/common/middleware/output_compliance_middleware.py`。
- 在各业务图的 middleware 链末尾启用。
- 对最终 `AIMessage` 内容进行审查、脱敏、改写或拦截。
- 对富输出附件事件进行审查，避免图表、表格、文件绕过文本审查。

当前项目已经有以下中间件基础：

- `PermissionMiddleware`：前置权限校验。
- `RichOutputMiddleware`：工具富输出拦截与上下文压缩。
- `SkillToolFilterMiddleware`：按 skill 动态披露工具。
- `MCPResilienceMiddleware`：工具异常降级。

输出审查网关应与这些中间件配合，而不是替换它们。

### 2. 规则引擎

第一阶段建议使用本地 Python 规则引擎，避免过早引入复杂依赖：

- `re`：手机号、邮箱、token、SQL、表结构、单位符号等规则。
- `pydantic`：审查请求、审查结果、规则命中项的数据模型。
- YAML / JSON 配置：维护风险类型、角色策略、脱敏格式和动作。
- 自定义词典：企业名称、排口名称、执法词、应急词、系统词。

当规则量明显增长后，再考虑：

- `casbin`：复杂 RBAC / ABAC 策略。
- `presidio-analyzer`：英文 PII 识别补充；中文个人信息仍建议用本地规则和业务词典。
- `sqlglot`：更稳健地识别 SQL 片段和表结构。
- `rapidfuzz`：企业名、排口名、内部字段名的近似匹配。

### 3. 语义审查器

语义审查建议使用独立的小模型调用，输入最终回答和上下文摘要，输出 JSON。它只做分类，不生成业务答案。

适合交给语义审查器的风险：

- 污染归因定责：是否把“相关性”写成“确认由某企业导致”。
- 内部执法信息：是否包含检查线索、处罚建议、执法安排。
- 实时预警信息：是否包含未公开应急响应、扩散预测、敏感调度。
- 健康建议：是否出现“绝对安全”“绝对无害”等绝对化承诺。

不建议交给语义审查器的风险：

- 手机号、邮箱、token、SQL。
- 单位符号和单位换算。
- 企业名 + 排口 + 小时值这类结构化模式。

## 四、核心架构

### 1. 分层链路

```text
LLM 最终输出
  ↓
OutputComplianceMiddleware
  ↓
文本规范化
  ↓
确定性 DLP 检测
  ↓
业务语义审查
  ↓
权限策略决策
  ↓
动作执行：放行 / 脱敏 / 改写 / 重生成 / 拒绝
  ↓
审计日志
  ↓
用户可见回答
```

### 2. 和工具输出的关系

最终输出审查不能只看最终文本。工具返回的图表、表格、附件也可能包含敏感数据。因此推荐增加两个审查点：

```text
工具调用结果
  ↓
ToolOutputLabeler：提取数据标签、敏感字段、来源、时间粒度
  ↓
RichOutputMiddleware：推送附件前审查 rich_outputs
  ↓
LLM 上下文只保留压缩摘要
  ↓
最终 OutputComplianceMiddleware 再审查自然语言回答
```

也就是说，输出审查网关应覆盖两类出口：

- **最终自然语言回答**。
- **前端富输出事件**，包括表格、图表、文件、地图和附件。

## 五、审查对象与数据模型

### 1. 审查上下文

建议定义统一的审查上下文：

```python
class ComplianceContext(BaseModel):
    request_id: str
    thread_id: str | None = None
    user_id: str | None = None
    tenant_id: str | None = None
    roles: list[str] = []
    data_scopes: list[str] = []
    channel: str = "internal"  # internal / external / public_api
    graph_name: str | None = None
    selected_skill: str | None = None
    intent: str | None = None
    permission_result: dict[str, Any] | None = None
```

### 2. 审查请求

```python
class ComplianceReviewRequest(BaseModel):
    context: ComplianceContext
    content_type: str  # final_text / rich_output / file / chart_data
    content: str | dict[str, Any] | list[Any]
    source_tool_names: list[str] = []
    evidence_tags: list[str] = []
```

### 3. 规则命中项

```python
class ComplianceFinding(BaseModel):
    rule_id: str
    risk_type: str
    severity: str  # low / medium / high / critical
    action: str  # allow / mask / rewrite / regenerate / block / escalate
    spans: list[dict[str, int | str]] = []
    reason: str
```

### 4. 审查结果

```python
class ComplianceReviewResult(BaseModel):
    decision: str
    safe_content: str | dict[str, Any] | list[Any] | None = None
    findings: list[ComplianceFinding] = []
    audit_summary: dict[str, Any] = {}
```

## 六、规则类型与处理策略

| 规则类型     | 示例                             | 检测方式                                  | 默认处理方式                       |
| ------------ | -------------------------------- | ----------------------------------------- | ---------------------------------- |
| 企业精确数据 | 企业名 + 排口 + 小时值           | 企业词典 + 排口词典 + 时间粒度 + 数值单位 | 按权限放行；无权限则脱敏或拒绝     |
| 内部执法信息 | 处罚建议、检查线索、执法安排     | 关键词 + 语义审查                         | 外部拒绝；内部按角色放行           |
| 污染归因定责 | “确认由某企业导致”               | 语义审查 + 证据标签                       | 无证据时改写为相关性或要求补充证据 |
| 实时预警信息 | 未公开应急响应、扩散预测         | 应急词典 + 时间敏感判断                   | 对外拒绝；内部记录审计             |
| 个人信息     | 手机号、联系人、邮箱             | 正则 + 字段名                             | 打码                               |
| 系统信息     | SQL、token、表结构、工具名、路径 | 正则 + 系统词典                           | 拒绝或删除片段                     |
| 单位错误     | mg/m3 与 μg/m3 混用              | 污染物单位规则                            | 拦截并要求重生成                   |
| 健康建议     | 绝对安全、绝对无害               | 关键词 + 语义审查                         | 改写为风险提示                     |

## 七、关键规则设计

### 1. 企业精确数据

企业精确数据不是“出现企业名就拦截”，而是看组合风险。

高风险组合：

```text
企业名称 + 排口/监测点 + 小时/分钟时间 + 污染物浓度/排放量
企业名称 + 在线监测 + 超标倍数 + 具体时间
企业名称 + 设施状态 + 异常排放 + 精确数值
```

建议策略：

| 用户类型              | 处理                                     |
| --------------------- | ---------------------------------------- |
| 企业本租户用户        | 只放行本企业授权范围内数据               |
| 属地监管人员          | 按行政区和职责范围放行                   |
| 平台管理员            | 放行但强制审计                           |
| 外部公众 / 未登录用户 | 脱敏企业名、排口和小时值，保留区域级趋势 |

脱敏示例：

```text
原文：A 企业 1 号排口 2026 年 05 月 19 日 10 时 NOx 为 126 毫克/立方米。
脱敏：某重点排口 2026 年 05 月 19 日 10 时 NOx 浓度处于较高水平，具体企业和排口信息仅对授权用户开放。
```

### 2. 内部执法信息

内部执法信息包括：

- 处罚建议、立案建议、移交建议。
- 检查线索、暗查计划、执法路线。
- 企业问题清单、未公开整改要求。
- 内部研判结论和监管调度。

默认策略：

- `external`、`public_api`：拒绝输出，并改为说明“该类信息仅对授权监管人员开放”。
- `internal` 且具备执法角色：放行，但记录高等级审计。
- `internal` 但无执法角色：拒绝或输出公开口径。

### 3. 污染归因定责

污染归因是高风险表达。系统应区分三种口径：

| 表达类型 | 是否允许        | 示例                                           |
| -------- | --------------- | ---------------------------------------------- |
| 相关性   | 一般允许        | “该企业周边监测值与污染时段存在同步升高现象”   |
| 可能贡献 | 需证据支撑      | “结合风向和浓度变化，该企业可能存在贡献”       |
| 确认定责 | 高权限 + 强证据 | “经现场核查和执法取证，确认该企业导致本次污染” |

没有 `official_investigation`、`inspection_evidence`、`causal_model_verified` 等证据标签时，禁止输出确认定责口径。

改写示例：

```text
原文：本次污染确认由 A 企业导致。
改写：现有数据仅能说明 A 企业周边浓度变化与污染时段存在相关性，尚不足以直接认定责任主体，需结合现场核查、排放台账和气象条件进一步验证。
```

### 4. 实时预警信息

实时预警信息包括：

- 未公开应急响应级别。
- 扩散预测、污染团传输路径、敏感点影响范围。
- 内部调度方案、管控名单。
- 尚未发布的预警解除或升级判断。

建议策略：

- 对外只允许输出已公开发布的信息。
- 内部用户按应急角色和行政区放行。
- 所有实时预警输出都记录审计日志。

### 5. 个人信息

默认打码：

| 类型   | 规则                          | 示例                 |
| ------ | ----------------------------- | -------------------- |
| 手机号 | `1[3-9]\d{9}`                 | `138****5678`        |
| 邮箱   | 常见邮箱正则                  | `zh***@example.com`  |
| 联系人 | `联系人/负责人/经办人 + 姓名` | `张某`               |
| 身份证 | 18 位身份证规则               | `110***********1234` |

### 6. 系统信息

系统信息应直接拒绝或删除，包括：

- SQL 语句。
- token、api key、secret。
- 表名、字段名、数据库结构。
- skill、tool、route、函数名、文件路径。
- 栈追踪、异常对象、接口原始响应。

当前项目已有输出提示词禁止泄露内部机制，但最终审查仍应做强制兜底。

### 7. 单位错误

大气业务单位必须硬规则校验：

| 指标  | 正确单位    |
| ----- | ----------- |
| PM2.5 | 微克/立方米 |
| PM10  | 微克/立方米 |
| NO2   | 微克/立方米 |
| SO2   | 微克/立方米 |
| O3    | 微克/立方米 |
| O3-8h | 微克/立方米 |
| CO    | 毫克/立方米 |
| AQI   | 无单位      |

拦截规则：

- PM2.5、PM10、NO2、SO2、O3 使用 `毫克/立方米` 或 `mg/m3`：拦截。
- CO 使用 `微克/立方米` 或 `μg/m3`：拦截。
- 同一指标在同一回答中混用单位：拦截。
- AQI 后面跟浓度单位：拦截。

处理方式：

- 如果可以确定正确单位，直接改写为中文规范单位。
- 如果数值可能涉及换算，要求模型重生成，不能静默换算。

### 8. 健康建议

禁止绝对化表述：

- “绝对安全”
- “完全无害”
- “不会影响健康”
- “任何人都可以放心外出”

推荐改写：

```text
当前空气质量风险较低，但敏感人群仍建议根据自身情况安排户外活动；如出现不适，应减少暴露并咨询专业医生。
```

## 八、权限决策矩阵

输出审查网关的动作应由“风险类型 + 严重程度 + 用户角色 + 渠道 + 证据标签”共同决定。

| 风险类型       | external        | internal 普通用户 | internal 监管用户       | admin                |
| -------------- | --------------- | ----------------- | ----------------------- | -------------------- |
| 企业精确数据   | mask / block    | mask              | allow + audit           | allow + audit        |
| 内部执法信息   | block           | block             | allow + audit           | allow + audit        |
| 污染确认定责   | rewrite / block | rewrite           | allow 需证据            | allow 需证据 + audit |
| 实时预警信息   | block           | block             | allow + audit           | allow + audit        |
| 个人信息       | mask            | mask              | mask / allow 需业务理由 | mask / allow + audit |
| 系统信息       | block           | block             | block                   | block                |
| 单位错误       | regenerate      | regenerate        | regenerate              | regenerate           |
| 健康绝对化建议 | rewrite         | rewrite           | rewrite                 | rewrite              |

## 九、处理动作定义

### 1. allow

直接放行，但可记录低风险审计。

### 2. mask

对敏感片段做脱敏，保留业务含义。

```text
13812345678 -> 138****5678
A 化工有限公司 -> 某重点企业
1 号排口 -> 某排口
```

### 3. rewrite

对高风险表达改写为合规口径，常用于归因和健康建议。

### 4. regenerate

当存在单位错误、格式错误、口径冲突时，要求模型基于原始安全上下文重新生成。建议最多重试 1 次，避免循环。

### 5. block

拒绝返回原内容，输出统一拒绝话术：

```text
该问题涉及未公开或受权限保护的信息，当前账号暂无查看权限。
```

### 6. escalate

返回“需要人工复核”或转人工流程，适用于审查器置信度低但风险高的内容。

## 十、审查配置示例

建议用 YAML 配置规则，便于后续运营调整：

```yaml
rules:
    pii_phone:
        risk_type: personal_info
        detector: regex
        pattern: "1[3-9]\\d{9}"
        severity: medium
        default_action: mask

    system_sql:
        risk_type: system_info
        detector: regex
        pattern: "(?is)\\b(select|insert|update|delete|drop|alter)\\b.+\\b(from|into|table)\\b"
        severity: critical
        default_action: block

    pollutant_unit_pm_mg:
        risk_type: unit_error
        detector: unit
        pollutants: ["PM2.5", "PM10", "NO2", "SO2", "O3", "O3-8h"]
        forbidden_units: ["mg/m3", "mg/m³", "毫克/立方米"]
        severity: high
        default_action: regenerate

policies:
    enterprise_precise_data:
        external: mask
        internal_user: mask
        regulator: allow_audit
        admin: allow_audit

    law_enforcement_internal:
        external: block
        internal_user: block
        regulator: allow_audit
        admin: allow_audit
```

## 十一、语义审查提示词设计

语义审查器应使用固定 JSON 输出，不允许自由发挥：

```text
你是大气环保智能体的输出合规审查器。只判断给定回答是否包含以下风险：
1. 内部执法信息
2. 污染归因定责
3. 未公开实时预警
4. 绝对化健康建议

请只输出 JSON：
{
  "findings": [
    {
      "risk_type": "...",
      "severity": "low|medium|high|critical",
      "evidence_text": "...",
      "reason": "...",
      "suggested_action": "allow|rewrite|block|escalate",
      "safe_rewrite": "..."
    }
  ]
}
```

注意：

- `evidence_text` 只截取必要片段，不输出长文本。
- 如果是污染归因，必须判断是否存在“确认由某企业导致”这类定责表达。
- 如果只是相关性分析，不应误判为定责。
- 如果无风险，返回 `{"findings": []}`。

## 十二、审计日志设计

建议每次审查都记录审计日志：

```json
{
    "request_id": "req_xxx",
    "thread_id": "thread_xxx",
    "user_id": "u_xxx",
    "tenant_id": "tenant_xxx",
    "roles": ["regulator"],
    "graph_name": "basic-qa",
    "selected_skill": "air-quality-basic-query",
    "content_type": "final_text",
    "decision": "rewrite",
    "risk_types": ["pollution_attribution"],
    "rule_ids": ["semantic_pollution_attribution_v1"],
    "severity": "high",
    "action": "rewrite",
    "content_hash": "sha256:xxx",
    "safe_content_hash": "sha256:yyy",
    "created_at": "2026-05-19T10:00:00+08:00"
}
```

审计日志原则：

- 不存完整敏感原文。
- 存 hash、片段类型、命中规则和动作。
- 高风险审计可附加少量脱敏片段。
- 支持按用户、租户、风险类型、时间范围检索。

## 十三、与当前项目的集成方式

### 1. 新增模块

建议新增：

```text
src/common/compliance/
  __init__.py
  models.py
  detectors.py
  policy.py
  masker.py
  semantic_reviewer.py
  audit.py
  unit_rules.py

src/common/middleware/
  output_compliance_middleware.py

static/compliance/
  output_rules.yaml
```

### 2. Middleware 顺序

推荐顺序：

```python
[
    SkillToolRegistryMiddleware(business_tools),
    PermissionMiddleware(),
    MCPResilienceMiddleware(_mcp_tool_names()),
    TimeContextMiddleware(),
    RichOutputMiddleware(),  # 后续应在推送附件前调用 rich_output 审查
    ExpandQuestionMiddleware(),
    ModeRoutingMiddleware(),
    CodeInterpreterMiddleware(ptc=[]),
    SkillToolFilterMiddleware(...),
    OutputComplianceMiddleware(),  # 最终出口审查
]
```

如果框架钩子无法稳定拦截最终消息，可以采用两步方案：

1. 先在业务 graph 外层包一层 `postprocess_final_response` 节点。
2. 后续再沉淀为 DeepAgents middleware。

### 3. 富输出审查

`RichOutputMiddleware` 当前会把 `rich_outputs` 推送到前端，并把工具上下文压缩。建议在推送前增加：

```text
rich_outputs
  ↓
ComplianceReviewRequest(content_type="rich_output")
  ↓
脱敏或拒绝附件项
  ↓
stream_writer(event)
```

避免图表、表格、地图、文件绕过最终文本审查。

## 十四、落地步骤

### 阶段 1：确定性规则 MVP

目标：先覆盖最容易出事故的硬规则。

- 个人信息打码。
- SQL / token / 表结构 / 工具名 / route 名拦截。
- 污染物单位错误拦截。
- 企业名 + 排口 + 小时值组合脱敏。
- 审计日志落本地 logger 或数据库表。

### 阶段 2：权限策略联动

目标：把前置权限和输出审查打通。

- 从 `PermissionMiddleware` 或 runtime config 读取用户身份、租户和权限结果。
- 支持外部、内部普通用户、监管用户、管理员的差异化动作。
- 企业精确数据和内部执法信息按角色放行或拒绝。

### 阶段 3：语义审查器

目标：覆盖需要语义判断的风险。

- 污染归因定责。
- 内部执法信息。
- 未公开预警信息。
- 绝对化健康建议。
- 支持 rewrite 和 block。

### 阶段 4：富输出和附件审查

目标：覆盖图表、表格、地图和文件。

- 审查 `rich_outputs` 中的表格数据。
- 图表标题、字段名、tooltip、下载数据均纳入审查。
- 文件类输出增加下载前审查。

## 十五、测试用例建议

### 1. 单元测试

- 手机号、邮箱、身份证打码。
- SQL 和 token 拦截。
- PM2.5 使用毫克/立方米时触发 regenerate。
- CO 使用微克/立方米时触发 regenerate。
- 企业名 + 排口 + 小时值在外部渠道触发 mask。
- skill、tool、route、路径等系统信息触发 block。

### 2. 集成测试

- 普通用户请求企业排口小时值，最终输出被脱敏。
- 监管用户请求辖区内企业排口小时值，放行并记录审计。
- 模型输出“确认由某企业导致污染”，无证据标签时被改写。
- 模型输出“绝对无害”，被改写为风险提示。
- 图表附件中包含手机号或企业排口精确值，推送前被脱敏或拦截。

### 3. 回归测试

- 普通空气质量查询不被误拦截。
- 区域级统计、城市级 AQI、公开数据正常放行。
- 工具失败时的业务化错误提示不被误判为系统信息。

## 十六、风险与注意事项

1. **不要只做最终文本审查**

    图表、表格、文件和前端事件同样是输出，必须纳入审查范围。

2. **不要让审查器看到过多原始敏感数据**

    语义审查器输入应尽量是最终回答和脱敏上下文，能用规则判断的不要送模型。

3. **不要静默修改可能影响事实的数据**

    单位错误涉及数值含义，无法确定是否需要换算时，应要求重生成，而不是直接替换单位。

4. **不要把审计日志变成二次泄露源**

    审计日志只存规则命中、风险类型、hash 和脱敏片段。

5. **不要把全部规则写进 prompt**

    prompt 只能降低概率，不能作为强制合规边界。强规则必须在代码和策略配置中执行。

## 十七、推荐最终形态

输出审查网关的最终形态应是一个可配置、可审计、可灰度的安全出口：

```text
PermissionMiddleware
  负责“能不能查”

SkillToolFilterMiddleware
  负责“能看到哪些工具”

ToolOutputLabeler / RichOutput 审查
  负责“工具结果能不能进入上下文或前端”

OutputComplianceMiddleware
  负责“最终回答能不能返回用户”

AuditLogger
  负责“出了什么风险、如何处理、谁触发的”
```
