# HY3 / DeepSeek 两轮测试独立复核

复核日期：2026-10-25（Asia/Shanghai）。本次只读核对报告、manifest、逐请求/调用/检查/资源记录、部分受控测试回答及检查实现；未启动服务、发送模型请求或修改原始结果。

## 核心结论

本轮完成了 Basic QA 的真实模型单用户探索对比，**没有完成此前讨论的并发能力测试**。两份 manifest 均为 `profile=S`、`concurrency=1`、`rounds=1`、`allow_load=false`。因此，目前不能据本轮回答“系统稳定支持多少并发、每分钟承载多少请求”。

DeepSeek 在这批题的单请求速度上整体领先，值得作为下一轮候选；质量只能表述为“现有自动检查通过数更多”。知识检索缺失、检查规则问题和未完成的历史预置使其不能成为完整产品质量或容量结论。

## 可信的测量结果

以下延迟为各轮按时完成且关联成功的样本，HY3 37 条、DeepSeek 38 条；不是全部发送请求的等待时间分布。每轮发送 40 道测量题，另有 50 条历史轮。DeepSeek 的具体请求模型为 `cn:deepseek-v4.1-flash`，网关成功响应回显 `deepseek-v4.1-flash`。

- 接口首正文 P50：HY3 29.095 秒，DeepSeek 15.4765 秒，下降 46.8%。
- 接口首正文 P95：109.680 秒 → 41.1956 秒；小样本探索值。
- 完整回答 P50：30.791 秒 → 16.958 秒。
- 完整回答 P95：111.6606 秒 → 42.07845 秒，下降 62.3%；小样本探索值。
- 按时流完成且回答关联：37/40（92.5%）→ 38/40（95%），仅差一道题，不足以认定稳定性显著提高。
- 自动回答检查通过：15/40（37.5%）→ 22/40（55%），不是人工核实的事实正确率。
- 两轮都完成的 35 道题中，DeepSeek 完整回答更快的有 27 道，HY3 更快的有 8 道。因此“整体更快”成立，“每题都更快”不成立。

对每条成功请求直接计算“完整结束减首正文”，中位数分别为 HY3 1.212 秒、DeepSeek 1.3275 秒。等待主要发生在首正文之前，但这不足以排除缓冲、分段发布策略或其他链路等待；不能单凭两个总体分位数接近断言流式传输无问题。

## 需要修正的原报告结论

### 1. 本轮没有并发结果

没有并发档位比较、持续负载、开放到达或长稳证据。单请求下 CPU 较低只能说明采样期间未见已采容器的 CPU 饱和，不能排除连接池、锁、worker 并发限制、身份接口/外部模型限流等问题。资源记录中的连接池等待、池占用和队列深度均为空，且未覆盖全部宿主进程。

### 2. 质量分数有检查规则偏差，也存在真实业务问题

Q4 两轮都是 2/10，但 `checks.jsonl` 中八道失败的具体原因并非原报告描述的“洛阳/增加/优良未复述”：

- HY3：七题含 `no_tool_call`，其中一题还缺“差”；另一题缺“15时”。
- DeepSeek：六题含 `no_tool_call`；另两题分别缺“15时”和“差”。

例如 BQA-033、BQA-034 的测量回答包含问题所需的变化或差值，却因末轮没有新工具调用而失败。能从可信历史回答的问题，不应仅凭末轮无新调用判错；是否必须重新取数应逐题确定。相反，BQA-032 的 HY3 回答把原来的日口径改成月口径，这是实际上下文问题，不能将所有失败都归咎于评分器。

BQA-036 使用真实 MCP 数据时，两模型都回答 08 时峰值，而检查仍要求合成 fixture 的“15时”。这属于数据来源与检查口径冲突；本次未独立重查 MCP 原始响应，不据此判定两份答案数值真实正确。

现有检查主要依赖关键词、工具次数和数字存在性，未逐题完成数值、范围、证据一致性审查。因此 22/40 不能解释为“真实正确率 55%”，也不能由完成率 95% 推出回答质量达标。

### 3. 中止原因的归因有误或证据不足

HY3 BQA-011 的原始 `aborted_reason=unit_too_large`。当前 `src/common/output_streaming/safety.py` 对应在输出单元超过硬限制且找不到安全分段边界时抛错；它属于流式输出安全分段问题，原报告“HY3 中止也是工具失败预算”的归因不成立。

DeepSeek BQA-017、BQA-029，以及 BQA-039 的第一条历史轮，原始原因均为 `generation_failed`。工具拒绝记录使“失败工具导致中止”成为候选解释，但该通用错误码不足以独立证明具体触发了工具失败预算。没有相应异常栈或细分原因链时应保留为待定位，不应直接宣布平台无故障。

HY3 另有 BQA-009 客户端超时、BQA-012 流协议错误，均应保留为产品故障线索。

### 4. 依赖共同缺失不代表比较完全公平

两轮都没有可用知识检索，但影响程度不同：HY3 调用了 knowledge_search 8 次；DeepSeek 调用了 18 次，且触发更多失败路径。因此能比较的是“知识检索不可用时的本产品表现”，不能直接外推到依赖完整时的模型排名。

两轮 Q4 虽然都发送 50 条历史轮，但 HY3 为 50 条完成，DeepSeek 只有 49 条完成，BQA-039 的历史首轮中止。后续 Q4 不能称为完全等价的已完成历史上下文。即使五条用户历史相同，两模型实际生成的助手历史也不同，这是本轮真实交互比较的一个变量。

预检数量也需更正：现存五个 HY3 预检目录分别有 2、2、2、1、1 条请求，合计 8 条；DeepSeek 预检另有 2 条。因此两轮预检共 10 条，不是粘贴交付总结所说的共 8 条。连同两轮各 90 条，已保存的业务请求记录共 190 条；另有执行者单列的两个网关探针，不混入业务分母。

### 5. 消耗与资源记录的解释范围

总 Token 为 HY3 3,452,712、DeepSeek 4,709,865，后者增加 36.4%；输入 Token 增加约 40.7%。这两个总量包括每轮 50 条历史轮，不是仅 40 道测量题的用量。

只看 40 道测量题：HY3 输入 1,753,759、输出 135,360，合计 1,889,119；DeepSeek 输入 2,422,741、输出 82,144，合计 2,504,885。失败尝试的部分 usage 缺失，全部费用仍未知，不能用网关倍率推断绝对价格。

两轮资源记录的实际相邻采样间隔中位数约 5.30 秒，而报告写 3 秒。manifest 的“每容器 4 CPU/1 GiB”也与报告及原始内存限额中不同容器的 2 GiB/1 GiB/512 MiB 不一致。DeepSeek LangGraph CPU 汇总均值 2.49%、峰值 12.87%，也不是报告所写的约 1%。这些问题不推翻单请求延迟，但需在容量测评前修正记录。

## 下一步应聚焦什么

1. 保留原始报告和分数；另立修正说明，不覆盖失败。
2. 补齐知识检索与正常权限，确认代表题能取得有效证据；完成历史预置校验。
3. 定位 HY3 分段中止、流协议错误及 DeepSeek 的 generation_failed；将语义复核与机械检查分别报告。
4. 按原规范 F 容量档逐步升压并验证稳定性，同时分开报告受控依赖平台承载与真实模型端到端结果。只交付实际完成的档位；预算不足时标记部分执行，不能再次用单并发替代并发验收。
5. 最终应给出在明确资源、题库、模型配额、成功率和延迟目标下的已验证并发/吞吐范围，以及第一个失败档位与原因。未测到边界则只报告下界，不宣称最大容量。
