# C 阶段性能验收报告（聊天 R + 6/7 固定规模 SQL）

时间：2026-10-21。执行范围按用户选择：聊天 R（40 案，并发 1/5/10，各 3 轮）+ Change6/7 固定规模 SQL 基准；预算 ≤120 分钟。未执行 F 开放到达、60 分钟稳定性、组合负载、真实浏览器并发或生产容量验收。

## 结论先行

- **C 未通过。** 聊天 R 在并发 1 达到 120/120，但并发 5 为 52/120、并发 10 为 29/120；两档均不满足 P 层每轮完成成功率 100% 的硬门禁，共 159 次 `503` 受理失败。失败轮次保留，未通过重试、降并发或删样本掩盖。
- **后台规模 SQL 当前 schema 为 3 FAIL / 2 PASS。** 按设计 D4 的固定规模与目标：`change6_list` P95 1222.1ms（目标 500）、`change6_aggregate` 2185.2ms（目标 1500）、`change7_leaderboard` 5778.4ms（目标 1000）未达标；`change6_content` 157.3ms、`change7_sources` 103.9ms 达标。
- **候选索引只能救回一部分。** 在隔离规模库试加 5 个索引后：list/content/sources 达标，aggregate 4186.0ms、leaderboard 4117.3ms 仍 FAIL；因此“加索引即可达标”不成立，聚合/榜单还需要预聚合或查询重写。产品迁移未改，候选索引只存在于一次性规模库。
- 本轮是固定规模 SQL 基准，不是 HTTP/API 全路径或生产容量结论；R 也不是容量/尾延迟承诺。Token 未采集。

## 后台 6/7 固定规模 SQL

### 当前 schema

| 查询 | P50 (ms) | P95 (ms) | 目标 P95 | 状态 |
|---|---:|---:|---:|---|
| change6_list | 841.3 | 1222.1 | 500 | **FAIL** |
| change6_aggregate | 1855.1 | 2185.2 | 1500 | **FAIL** |
| change6_content | 109.2 | 157.3 | 500 | PASS |
| change7_leaderboard | 3768.4 | 5778.4 | 1000 | **FAIL** |
| change7_sources | 65.1 | 103.9 | 500 | PASS |

70 个样本/查询，10 并发，无 SQL 错误。单条执行计划显示：list 对 100k request 做 Seq Scan 后 top-N 排序（单条约 44ms）；aggregate 对 300k attempt、1M observation 做并行 Seq Scan（单条约 174ms）；leaderboard 对 200k intent 与 200k assignment 做并行 Seq Scan、Hash Join 和外部排序（单条约 225ms）。单条不慢，10 并发下 CPU/IO 竞争把 P95 推到目标外，说明固定规模下缺少支撑索引/预聚合。

### 候选索引复测（只在隔离规模库）

试加（未迁移到产品）：

- `agent_requests (tenant_id, admitted_at DESC, id DESC)`
- `agent_run_attempts (tenant_id, admitted_at)`
- `agent_model_observations (tenant_id, started_at)`
- `agent_question_intents (tenant_id, analysis_version, action, object, request_id)`
- `agent_question_assignments (tenant_id, status, intent_id)`

| 查询 | P95 (ms) | 目标 | 状态 | 相对当前 schema |
|---|---:|---:|---|---|
| change6_list | 8.4 | 500 | PASS | 1222.1 → 8.4 |
| change6_aggregate | 4186.0 | 1500 | **FAIL** | 2185.2 → 4186.0（未改善） |
| change6_content | 5.5 | 500 | PASS | 157.3 → 5.5 |
| change7_leaderboard | 4117.3 | 1000 | **FAIL** | 5778.4 → 4117.3（仍超 4 倍） |
| change7_sources | 18.8 | 500 | PASS | 103.9 → 18.8 |

索引对点查/列表有效，但 aggregate 仍需分别 count 三张表，leaderboard 仍需对全量 intent 分组；两者在 10 并发下的 CPU/排序成本没有被 btree 消除。**最小下一步不是继续堆索引**：aggregate 应改为按窗口维护汇总计数（或对三表分别做覆盖索引 + 预聚合）；leaderboard 应按 `profile/analysis_version/window` 维护簇计数/请求去重计数，或改为物化视图/汇总表并在写入侧增量维护。任何方案都需新迁移、空库/存量升级验证和同规模复测，本轮未改产品代码。

### 口径限制

- 这是**固定规模 SQL 基准**，不是 admin HTTP API 全路径；没有计入 FastAPI、IAM 实时鉴权、BFF、连接池排队和 JSON 序列化，也没有跑真实浏览器。实际 API 可能更慢，不能把这里的 PASS 当作接口 SLA。
- 查询是 6/7 关键查询形状的固定复现，不是所有产品查询的逐字复制；`change6_list` 使用 request 列表形状，实际运营页用户列表还包含 attempt/observation/cost 多段 CTE，实际成本可能更高。
- 规模 PG 为 4 CPU/1024 MB 单容器，结果依赖该资源规格；不是生产硬件容量结论。
- 每组 70 样本 <200，P95 是探索值；只用于固定规模的失败定位，不用于稳定 SLA。
- 未执行 F 开放到达、突发、60 分钟稳定性、组合负载、真实浏览器并发；这些不能由本轮 R/SQL 结果替代。

证据：[C-scale-6-7-20261021.json](C-scale-6-7-20261021.json)、[C-scale-6-7-after-indexes-20261021.json](C-scale-6-7-after-indexes-20261021.json)。基准脚本为私有 `.local/campaign-20261021/scale_bench2.py`（含凭据读取，不提交）。
