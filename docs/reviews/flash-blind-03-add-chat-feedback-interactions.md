## 阻断问题

### R01 / P1：意见读取绕过双权限门槛

位置：admin/api/app/routers/feedback.py:170；services/feedback.py:560。路由只要求agent:content:read，服务随即调用会无条件打开运营GUC的_enable_operations_read。**只有原文权限、没有运营权限的合成成员，操作列表403，但另一成员意见接口200，能看到审核者的合成私有意见。** 违反本项明确的“运营+原文”授权。修复必须先校验两种权限；本人读取自己意见可以独立采用本人路径，不能由此开启整个企业运营读取。

证据：backend-probes.json/comment_permission_split，comment-permission-probe.txt，独立反例1失败。不是跨企业泄漏的推断，是同企业内越过运营权限的实测。

### R02 / P1：CAS不是原子操作

位置：services/feedback.py:263–274。读current后在Python比较revision，没有行锁或条件更新。调度器仅让两个真实PG读同时完成，不修改数据库返回值；两笔expected_revision=1的新操作均200，均返回revision=2，历史为[1,2,2]。正确结果应一笔成功、一笔409，或串行重新校验后拒绝旧版本。现有测试“两个页面”实际顺序发送，不能证明并发。

证据：backend-probes.json/concurrent_cas；admin-and-probes.txt。通用浏览器入口还允许省略expected_revision绕过CAS，需要统一收口。

### R03 / P1：幂等摘要与结果不完整

位置：services/feedback.py:229–252。只比较rating/reason，未比较目标回答、意见正文或完整操作语义。同操作ID更改意见200、更换目标回答200且返回旧回答；之后的新修改完成后，重投旧操作返回最新revision/rating，未复用原受理结果。需要持久化规范操作摘要（意见只存摘要，不能进事件）及原结果，先检查归属/删除，再决定合法复用；不能把幂等理解为按operation_id返回任意当前状态。

证据：backend-probes.json/idempotency。原revision=1，后修改revision=2，旧操作重投返回2/positive。

### R04 / P1：复制/计时缺跨请求幂等与outbox

位置：services/ledger.py:2213、2317、2362。只做批内seen去重，直接INSERT事件，没有持久化幂等裁决、逐项保存点或对应outbox。实测首复制200但outbox=0；同事件跨请求重投500；“合法新复制+旧事件重投”整批500，新合法事件也回滚为0。这会在正常网络重试中丢采集，并破坏事件投递契约。

另一个真实反例：313,622字节的30条合法单条事件超过256KiB批限，仍返回accepted=true、written=30；受理循环忽略validate_batch的整体超限结果，最后还改写成ok。需要区分批次硬限制与可逐项受理的普通非法项。

应统一事实/事件/outbox同事务，并发重复也应复用；同ID异事实明确冲突；各项失败不牵连合法邻项。另有代码上的契约不一致：反馈服务写browser.feedback时source=server，但登记只允许browser，必须将实际写出的事件加入三侧契约验证，而非只测试手工样本。

证据：backend-probes.json/copy_replay_and_outbox。

### R05 / P1：删除禁读、晚到处理和父子完整性失效

删除接口已200后，旧评价重投仍200，历史仍可见1条、晚到timing仍accepted，反馈统计仍有1个可评价回答。列表/指标未过滤永久删除，幂等返回在删除检查之前，timing没有线程删除复核。

此外0011_feedback的current表**没有任何外键**，实际删除合成父answer后current仍残留1行，不能靠operations/comments的级联保证current清理。三个表仅ENABLE RLS，pg_class的FORCE全为false，和已勾选任务/报告不符。需要新增修复revision补同租户关联、清理策略、FORCE及恢复流程；0011已执行不能倒改。

证据：backend-probes.json/deletion、rls_and_parent_integrity；environment.json；integrity-probe.txt。删除竞态、重放、恢复旧备份仍须完成本域演练，不能引用旧台账演练替代。

### R06 / P1：复制指标队列不一致，实际可达200%

位置：services/feedback_metrics.py:135–147。分母是窗口内确认的回答，分子却是窗口内复制的所有回答，未限制到同一可复制队列。用2个旧回答在新窗口复制、1个新确认回答未复制，实测返回eligible=1、distinct=2、copy_rate=2.0。

应按默认回答cohort统计复制，按复制操作时间的活动次数另行命名，不混分母。删除、启用时间、样本/缺失和计时去重亦需统一；当前missing把invalid再次相减，measurement与attempt/回答数量混用。采集启用时间硬编码2026-10-13T14:00Z，不能代表不同租户/部署的实际启用事实。

证据：backend-probes.json/copy_cohort；同一例还证明复制occurred_at未来100天仍受理。

### R07 / P1：前端作用域竞态和迟到映射

位置：frontend/lib/feedback/client.ts:71–128及flushQueue。独立运行真实编译的client代码，只用受控fetch改变响应时序，复现：

1. A映射请求迟到，切到B后仍把A回答写入当前缓存。
2. 第一次查询未找到回答后写永久负缓存，之后服务端已确认也不再查询，评价仍不可用。
3. 全局scopeAtCall被另一个请求覆盖，旧A反馈响应在B作用域仍返回ok。
4. 旧A批次成功回调按数组位置splice了B的新队列；B事件未发送就消失。

必须每个请求/批次捕获不可变scope+epoch，取消/丢弃旧响应，按事件身份移除队列，负缓存有到期/明确重读。存储身份声明应与BFF真实会话裁决一致，切换不能把旧操作重绑到新上下文。source测例是客户端调度证明，不冒称完成真实多标签页浏览器验收。

证据：client-probes.json、client-under-review.js、client-probes.cjs。

### R08 / P2：计时、失败反馈和部署交接尚不完整

首正文计时在chat-store收到流事件时、React setState之前打点，不是DOM可见；页面卸载的abandonTimingsOnUnload未见实际接线，队列按条数未实现256KiB分批。显示完成/未完成、有限数值、时间顺序、运行起点/保留期和删除关联需补强。点赞/撤销失败提示只在点踩详情框里，常规点赞失败没有可见恢复说明；编辑点踩但没保存就显示“已踩”，冲突后没有权威强制回读路径。

BFF写Origin硬编码localhost:3103，不能直接作为主工作区/生产环境接线；design要求默认关闭及真实启用时刻，但实现没有部署开关。contract-extension.md未更新实现版，报告live指标旧数字与实际JSON快照也不同。这里是源码/规格缺口，不把未做浏览器复现的每项都冒称已实测。
