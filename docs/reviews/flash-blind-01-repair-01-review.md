## 仍须修复的发现

### F01 / R01：409 补偿重新打开历史线程认领越权（P1，阻断）

位置：`frontend/app/api/[..._path]/route.ts:192`，`src/common/identity/langgraph_auth.py:211`，`src/common/identity/db.py:47`，`src/common/artifact_http.py:135`。

真实复现：Bob 创建并确认一个带合成私有标记的线程；仅删除该测试线程的归属行，模拟未知历史。Alice 读取为 404；随后经聊天代理 `POST /api/threads`，使用相同 ID 与 `if_exists=raise`，最终返回 **200**，Alice 再读取也为 **200**，两次均能看到 Bob 的合成私有标记。

原因：创建钩子先插入 Alice 的 `native_pending`，平台因已有线程返回 409；代理将任意 409 当成“上次成功但确认丢失”，调用内部确认端点。端点只查这条 pending 行并升级，没有证明平台对象是本次调用所创建。内部 token 防止直接调用，挡不住受信代理替攻击者确认。`live-claim.json` 保存状态与标记布尔值。

现有 `test_live_unknown_history_claim_denied` 只测原生 strict 创建后尚未确认的读取，因此可以通过，同时真实代理越权仍成立。必须补完整 BFF 分支回归。补偿应依赖可信创建事实/唯一操作凭证；不能把未知对象、403/409 或仅有 pending 当成功依据。同时覆盖创建响应丢失、确认失败、并发、恶意同 ID 重试，保持失败关闭。内部确认必须绑定经验证的实际创建事实与可信作用域。

### F02 / R04：运行中撤权尚未贯通到权限变更与全部外呼（P1，阻断）

位置：`admin/api/app/routers/roles.py:313`（权限替换）、`:235`（角色删除），`src/common/business_graph/nodes.py:303` / `:361`，`src/common/text_reduction.py:75`，`src/common/identity/runtime.py:160`。

1. **真实 PG + 实际管理路由：** 签发运行票据后，以 `PUT /roles/{tenant_admin}/permissions` 收回权限，接口 200；下一个管理请求已 403，但成员 revision **1→1**，同一票据所对应的旧 RuntimeIdentity 经真实身份库复查仍通过。角色权限修改和删除没有推进受影响成员/企业修订，新增“比较修订号”无法察觉这类撤权。证据 `admin-proofs.json`。
2. **实际节点/模型调用函数，模拟状态与模型：** 首次外呼失败后把实时身份修订改为已撤销，节点仍发送第二次模型调用；两次外呼只查身份一次。检查放在整个重试循环之前，空回复重试同样没有再次检查。不是实测 LLM 或生产撤权，但真实调用路径已执行。证据 `runtime-proofs.json`。
3. **实际摘要函数，模拟模型：** 强制身份模式下，无运行身份仍调用摘要模型 1 次、身份检查 0 次。长会话摘要和大输出整理直接调用 `summarize_complete_text`，未接入外呼守卫。还应核查技能路由等运行期外部调用，区分与用户请求无关的启动索引构建。
4. 修订快照缺失时仍仅查 active，升级前旧运行上下文可以沿用已失效授权。反例中四种实时修订均改变但仍放行。旧运行应安全停止/重新建立身份；不能用缺失快照避开撤权。测试 fixture 也应携带完整快照。

正向进展：新增修订比较测试、真实 create_agent/Pregel 上下文测试通过，原来的 Runtime.config 形状问题已有有效修复；这不等于六图与辅助调用均通过。权限变化应与修订/审计处于同一可靠事务；守卫应在每次实际发送前生效，拒绝结果不可被普通瞬时错误重试吞掉。

### F03 / R06：迁移 API 先于归属提交，失败项又被台账短路（P1，阻断）

位置：`admin/api/scripts/migrate_identity.py:478` / `:500` / `:539` / `:290`，`src/common/identity/langgraph_auth.py:262`。

脚本在一个未提交事务中写 `source=migrated` 归属，立即通过另一个服务调用原生 PATCH。原生 auth 使用另一条运行角色连接，读不到未提交行，拒绝迁移。**当前实际原生 API 的合成线程实测：提交前 PATCH 403，提交后 PATCH 200，清理 204**（`migration-live.json`）。这证明新迁移票据本身能在当前平台工作，失败来自事务安排。

另在专用 PG 库运行实际 MigrationRunner，以独立 runtime 连接模拟真实 auth 的可见性：首次 `metadata_pending=1`；再跑同一 manifest，返回 `already_applied=true`，API 回调总次数仍为 **1**（`migration-proofs.json`）。失败项也把 manifest 登记为 applied，复跑不会重试，和报告中的“复跑重试”相反。当前 stub 没有检查归属事务可见性，因而掩盖此问题。

应先可靠提交受控迁移阶段，再执行平台窄更新；为每个待处理实体持久化状态，失败/中断后继续未完成项，全部确认后才称 manifest 完成。覆盖响应丢失、API 403/503/超时、进程中断、复跑后补偿、归属冲突，保留历史正文与角色/身份边界。不能退回直接写平台私有表。还应核对历史归档与计算记录的租户回填一致性。

### F04 / R11：停用企业仍可创建角色（P1，阻断）

位置：`admin/api/app/routers/roles.py:34` / `:136`，`admin/api/app/deps.py:98`。

专用 PG + 实际路由：将合成企业设为 suspended，正确带当前企业/version 请求头，部门创建 **403**，但企业角色创建仍 **201**。角色 router 仅校验请求上下文，权限检查不验证 tenant 是否 active。R11 修复覆盖部门及部分成员入口，未收敛所有企业业务入口。

应审查企业角色创建/修改/删除/授权及其余企业业务操作：企业或成员停用后拒绝；保留平台管理员在明确平台入口对停用企业进行恢复/管理的能力。不能简单给所有路由套 active 依赖而阻断平台恢复。

### F05 / R10：不明确的停止结果仍被当作确认（P2，需闭环）

位置：`frontend/lib/chat-store.ts:65` / `:73`，`frontend/lib/langgraph-api.ts:157`。

实际 store 执行、服务替身：取消抛 409 时直接 confirmed=true；状态 `{found:true,status:null}` 或 `{found:false,status:null}` 也均为 true（`stop-proofs.json`）。本系统 **409 同时表示企业上下文变更**，不能仅按状态码认定后端进入终态。缺失状态、无权/不可见与已取消也是不同事实；没有活动 run_id 的列表查询还可能与提交或元数据到达竞争。

需要核验实际原生取消响应并区分业务错误语义，查到可信终态才确认；上下文冲突、未知/不可见、查询失败、提交尚未确认应返回未确认或明确安全收敛。补真实取消/企业切换/迟到 run_id 竞态测试。当前新增测试把任意 409 预设为“已终态”，未证明该假设。
