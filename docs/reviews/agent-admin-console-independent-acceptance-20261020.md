## IAM A11：实际接口与撤权语义

真实资源仅为本轮自建 PG25436、IAM29100、Redis26384。测试账号是新建合成账号，不使用正式 root 或其口令。

普通权限目录没有任意 POST 注册接口，因此通过追加版本化迁移登记 `agent:feedback:manage`：tenant scope、可下放、无 resource_code、不自动授予任何现有角色/root。授予与回收走正常角色创建、成员角色分配 HTTP API；Python 管理 API 每请求真实内省。

实测：未授 403 → 授予角色、重新登录后 200 → 回收角色后旧会话下一请求 401 → 重新登录后缺码 403。内省的精确管理码分别为无/有/无。应用会话桥接使用现有 `_establish_session`，本轮不声称又验证了完整浏览器 SSO；业务回答为合成夹具，不是三图真实运行。

原计划笼统写“撤码下一请求403”，与现有 IAM 的成员修订使旧会话失效语义不一致。本轮文档明确区分401和403，不修改鉴权协议、不放宽失败关闭。

另发现：平台管理员编辑既有企业角色权限的正常 API 在本次隔离实例触发 `role_permissions` RLS 403（原始 iam-feedback.log / PG 错误记录）。创建独立管理角色并分配/回收成员角色可行。该旧编辑路径问题没有藏掉或修成旁路；用户本次只授权 IAM 窄目录迁移，暂未扩改 IAM 授权服务。
