# 个人 AI 开发经验总结

> 面向团队演示 · 基于 Claude Code + OpenSpec + Superpowers 的实践心得

---

## 一、核心工具栈

| 工具            | 定位              | 特点                                        |
| --------------- | ----------------- | ------------------------------------------- |
| **OpenSpec**    | 需求 / 计划编排器 | 轻量、清晰、省 Token，（SDD）专注「做什么」 |
| **Superpowers** | 强制流程执行框架  | 测试驱动开发（TDD），专注「怎么做」         |
| **Claude Code** | 主交互终端        | 承载多模型、多上下文窗口的执行入口          |

### OpenSpec vs Superpowers 我的理解

- **OpenSpec**：偏「项目经理」角色 —— 把模糊需求结构化成清晰的计划文档，简单稳定。
- **Superpowers**：偏「流程督军」角色 —— 用 TDD 强制约束 AI，结果质量更可控。
- 一个负责「定义清楚」，一个负责「做得扎实」，两者互补而非替代。

## 二、标准工作流（OpenSpec 主线）

```
explore  →  propose  →  apply  →  archive
 探索       计划         实现      归档
```

1. **explore**：与 AI 多轮对话，定位问题 / 探索代码。
2. **propose**：需求对齐后，输出结构化的 proposal 计划文档。
3. **apply**：按计划执行落地。
4. **archive**：完成后归档，沉淀为可追溯的变更记录。

### ⭐ 核心理念：写计划，远比写代码重要

> **需求拆解得是否清晰、计划写得是否到位，决定了 AI 编码的最终质量。**
> **代码实现只是「按图施工」，真正的胜负手在前面的 explore 和 propose 阶段。**

- **AI 不缺写代码的能力，缺的是「明确的目标」**：模糊的需求 → 模糊的实现 → 反复返工，Token 全部浪费在沟通成本上。
- **计划写得好，弱模型也能跑出强结果**：拆解到位、上下文充分、边界清晰，执行阶段对模型能力的依赖会大幅下降（这也是第五节模型选型策略的根基）。
- **计划写得差，再强的模型也救不回来**：方向错了，跑得越快离目标越远。
- **所以我的精力分配是**：**70% 花在 explore + propose，30% 花在 apply + review**。

> 一句话总结：**先把「做什么」想透彻，「怎么做」交给 AI 即可。**

## 三、两种典型开发场景

### 场景 A：简单需求 / Bug 修复 —— 仅用 OpenSpec

适用：bug 修复、小需求、对精度要求不极端的场景。

**理由**：OpenSpec 足够轻量，**Token 成本低**，不需要 Superpowers 那套重型 TDD 流程。

**流程**：

1. 与 AI 对话探索问题（explore）
2. 多轮需求对齐后，制定 propose 计划
3. 执行 apply
4. archive 归档
5. **新开一个全新上下文窗口，执行 review 命令对本次改动做独立代码审查**（详见第四节）

> 即便是简单需求，OpenSpec 全流程跑完后我也会强制走一遍独立 Review，作为兜底。

### 场景 B：复杂全新需求 —— OpenSpec + Superpowers 组合拳

适用：全新功能、需求分析量大、对结果质量要求高的场景。

**理由**：

- 用 OpenSpec 把需求**定义清楚**（它在任务定义上更稳定、更清晰）
- 用 Superpowers 的 **TDD 流程**保证实现质量
- 两者协同：清晰的需求 + 严谨的执行 = 高质量交付

## 四、针对弱模型的补救方案：独立 Review 步骤

### 背景

Claude Code 接入不同能力的模型时，输出质量差异明显。**国产模型作为执行端时，需要额外的质量兜底**。

### 做法

1. 主流程结束后，**新开一个全新上下文窗口**
2. 执行自定义的 review 命令
3. 每个项目维护一份专属的 `review.md`，针对该项目的特点定制审查规则
4. 由「无上下文、无幻觉」的 AI 独立审查代码质量

### 价值

- 隔离上下文，避免「自己审自己」的偏见
- 项目级 review.md 让审查标准与项目特性强绑定
- 大部分需求经过这一步后，质量都能达标

---

## 五、模型选型策略：分阶段用模型，平衡成本与质量

### 核心思路

> **大脑用强模型，手脚用便宜模型**

- **需求 / 计划阶段**：优先使用 GPT-5、Claude 等海外强模型编写 OpenSpec 需求
- **执行阶段**：切换到国产模型完成 apply 落地

### 为什么这样做

- 全程使用海外强模型 → **成本过高，不可持续**
- 强模型把计划拆得足够细 → 执行阶段对模型能力的要求大幅下降
- 计划质量决定上限，执行模型只需「按图施工」即可

---

## 六、经验沉淀：为什么这套流程有效

1. **省 Token = 省钱**：简单任务不上重型流程，把预算花在刀刃上。
2. **流程分层**：定义、执行、审查解耦，每一步都用最合适的工具与模型。
3. **质量兜底**：独立上下文 review 是对抗幻觉与模型能力不足的关键一环。
4. **项目化定制**：每个项目的 `review.md` 让 AI 审查不再是空泛的代码规范检查。
5. **成本可控**：强弱模型搭配使用，让 AI 工程化真正可持续落地。
