# 企业化工程：多对话并行实施安排

日期：2026-10-12。适用于用户在不同工具中开启多个实现 Agent 对话；不要求使用同一模型，也不依赖工具内建的子 Agent 调度。每个对话领取一个完整 OpenSpec 实施包。

1 和 2 涉及身份、运行入口、共享代理及迁移，当前安排是顺序实施。可以提前写候选接口和测试样本，不能把基于假接口的实现当成联调完成。第 10 项提前写验收脚本是准备工作，不代表最终交付验收已通过。

## 2. 每个对话需要自己的工作区和测试环境

- 从同一已验收基线建立独立 Git worktree/checkout 和分支；仅开两个对话但仍编辑同一目录不能隔离冲突。
- 分别配置测试数据库（优先独立库）、服务端口、Redis/队列命名空间、输出目录和必要的 Trace 测试范围。不要让每个 Agent 运行默认 compose 后共同占用或重置同一测试数据。
- 每份提示词只授权一个 change，写出依赖提交、可改文件/模块、契约版本、测试范围和共享文件负责人。
- 所有者在自己的工作区验证和保留 diff，不合并别人的结果；使用冻结样本模拟另一个领域时明确标记，最终实际联调由集成者做。
- 对话之间可提交“需要公共接口增加什么”的清单，由协调者批准契约变更并安排接线；不能各自偷偷改共同假设。

## 3. 第 3/5 项的具体分工

| 区域 | 第 3 项：反馈 | 第 5 项：观测 | 集成者 |
|---|---|---|---|
| 业务模块 | 独立反馈服务、路由、模型与聊天交互组件 | 独立观测适配、usage/价格/Trace/Skill/MCP 归因 | 模块注册与共享接线 |
| 事件 | browser feedback/copy/timing 类型与局部样本 | runtime model/skill/tool 类型与局部样本 | 总登记/schema 兼容及公共消费者 |
| 共享入口 | 提交明确的 UI/store 接线需求 | 提交明确的 runtime hook 接线需求 | chat-store、代理、lifecycle hook、main、权限字典 |
| 迁移 | 独立 revision，自己的测试库验证 | 独立 revision，自己的测试库验证 | revision/head 合并，部署与组合回归 |
| 配置依赖 | 声明所需非秘密配置/依赖 | 声明所需非秘密配置/依赖 | 根配置、compose、uv.lock/package-lock |

规划第二项时要求新域独立模块，避免所有 Agent 都改同一 models.py。两个 Alembic 分支可在各自库验证；最终必须由集成者统一迁移链，不无说明改写已执行 revision。默认集成者为负责协调与独立验收的对话，实际合并需由用户授权该阶段工作。

## 4. 收件与验收顺序

1. 收到各 Agent 的匿名轮次、基线、diff、测试/联调报告及未完成项；先独立审查，不根据模型自述打分。
2. 各 change 的相关检查通过后，集成者处理共享接线、迁移和契约扩展，记录结果来源。
3. 从统一提交重新验证 A/B 隔离、提问→运行→回答→反馈→usage/Trace 全流程；单分支通过不代替集成通过。
4. 完成独立盲评记录后再揭晓模型；不同 change 难度/外部材料不相同，不直接按耗时排名。

首轮建议两个实现 Agent 并行，确认交接和集成顺畅后，第二轮再扩至三个。准备工作可与当前实现同时做；依赖还在变化的共享代码不提前并行实施。
