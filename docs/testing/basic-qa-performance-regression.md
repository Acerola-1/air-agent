# basic QA 并发性能回归规范

版本：v1.2；制定日期：2026-10-20；适用 Graph：`basic-qa`。

本规范用于建立基线、执行版本回归和发现容量边界。它规定以后每轮测试的输入、指标、判定和报告，不表示当前系统已达到文中的目标，也不表示压测工具已经实现。每次执行都必须产出一份[测试报告](templates/basic-qa-performance-report.md)，失败、中止、依赖不可用也要留报告。

## 1. 测试范围与当前依据

- 主测试走浏览器实际使用的同源 BFF → 受理/选择快照 → 原生运行/流式链路，保留 Java IAM、权限复查、台账、PostgreSQL 持久化和观测。直接 `graph.ainvoke()` 只用于局部定位，不作为端到端容量证据。
- 当前图入口见 [graph.py](../../src/basic_qa/graph.py)，节点流见 [builder.py](../../src/common/business_graph/builder.py)：意图判断、按需 Skill 路由、模型调用与工具循环、台账收尾。调用次数取实测，不能假定一次提问只有一次模型调用。
- [已有验收](../reviews/agent-interactions-observability-takeover-acceptance.md)仅覆盖局部开销及特定联调，未建立生产并发/长时负载基线。旧基准可能引用退役身份接口或测试资源，不直接运行。
- [模型观测规格](../../openspec/specs/agent-model-observability/spec.md)、[浏览器计时规格](../../openspec/specs/agent-chat-interaction-events/spec.md)约束指标口径。部分主规格仍有历史“六图”或旧模块描述，本规范范围以当前 `langgraph.json` 的 `basic-qa` 为准，不恢复旧路径。
- `add-agent-admin-console` 仍是活动计划；不能依赖尚未实施的性能页面。报告可由测试端、受控观测和只读导出生成。

### 1.1 两层证据分别出结论

| 层次 | 依赖与目的 | 不能推出的结论 |
| --- | --- | --- |
| P：平台承载 | 真实隔离 IAM、数据库、Redis、官方运行平台和 BFF；模型/MCP 用协议兼容、可控延迟/流块/错误的测试服务；有路由 Embedding 时也需明确受控 | 不能据此承诺真实模型的容量、语义路由准确率或回答质量 |
| E：真实端到端 | 使用真实配置的模型网关、Embedding 和实际 MCP 测试服务/授权测试数据；完整用户链路 | 外部限流属于当前部署容量约束，不能仅据此认定平台代码慢 |

P 层模型不能立即返回固定文本：必须冻结首块延迟、分块间隔、输出长度、工具规划轮数与失败规则，并记录测试服务版本。E 层若某依赖被替代，单列为受控组合，不称完全真实端到端。

## 2. 环境、资源和可比性

执行前读取 [正式运行态](../CURRENT-RUNTIME.md)及其指向的三仓清单；它们用于识别保护对象，不能作为测试资源配置。测试仅新建本轮所有的空临时资源，记录所有者、唯一名称、回环端口、数据库/角色/卷以及回收步骤。不能向正式库造数、复制正式凭据/业务原文、重建旧评测栈或回退 local 鉴权。

运行路径使用当前受支持部署方式；普通环境启动/状态只使用 `deployment/run_separated_local.py start|status`，不能为了压测直接启动正式服务、重配正式 DSN 或用全量编排重建依赖。独立测试部署必须显式指定自有资源，并在发压前验证实际实例身份，不以 `.env` 文件名代替验证。

每轮冻结以下信息，写入 `manifest.json` 和报告：

| 类别 | 必填内容 |
| --- | --- |
| 代码与运行来源 | 分支、HEAD、脏工作区文件清单及非秘密源码快照摘要；服务启动时间、镜像摘要、实际挂载/构建来源；避免旧进程冒充当前代码 |
| 软件 | Python/依赖锁摘要、官方 LangGraph API 镜像、数据库版本、BFF 构建版本、测试工具版本 |
| 硬件与配额 | CPU 核数、内存、容器/虚拟机限额、实例/worker 数、数据库连接池配置；压测端配置；同机其他任务 |
| 外部依赖 | 实际模型/provider/网关版本、已知 RPM/TPM/并发限制、超时/重试、MCP 与 Embedding 版本；未知填未提供 |
| 业务输入 | 问题集/测试数据/评分规则摘要、比例、上下文和输出长度预算、Skill/MCP 选择模式、用户/企业分布、缓存冷热、观测开关 |
| 测试策略 | 层次、档位、到达序列/随机种子、时长、样本下限、截止时间、采样间隔、阈值、预算上限、基线报告和判定规则 |

凭据只记录受保护配置的引用，不记录值。公开报告使用合成数据、主体别名与脱敏标识；普通明细不含问题/答案正文、Cookie、Token、请求头或内部推理。

比较双方必须使用相同协议/入口、资源、依赖版本/配额、负载、数据集、缓存策略、观测及评分口径。不同模型/机器/问题集建立新系列；外部模型标识相同但服务状态漂移也要记录。平台版本本身是被测变量，其余变化需解释。依赖切换导致不可比时，分别报告绝对结果并重新建基线，不能宣称性能回归通过。

## 3. 固定问题集与成功定义

### 3.1 v1 默认负载

固定使用 [basic QA 参考题库](basic-qa-reference-questions.md)及其 JSON 输入/合成数据，版本 `bqa-reference-202605-v1`。40题每类10题、混合权重各25%，不得由执行 Agent 临时自由出题。这只是初始标准负载，不代表已验证的用户流量。以后按真实分布调整须升问题集版本，并保留旧集回归。今日分支时钟、真实数据与合成数据不可比的限制按题库执行。

| 分类 | 输入要求 | 核验重点 | 提交至完成默认截止时间 |
| --- | --- | --- | --- |
| Q1 简单问答 | 固定知识问题，输出要求不超过 300 个汉字 | 核心事实、无编造、实际工具行为 | 60s |
| Q2 单步数据查询 | 固定时空范围、可核验的测试数据，输出不超过 500 字 | 实际查询、范围/数值/单位/来源正确 | 120s |
| Q3 多步骤问答 | 需要多项查询/对比，输出不超过 800 字 | 查询完整、计算正确、无遗漏或无证据断言 | 180s |
| Q4 多轮问答 | 使用参考题库 JSON 内固定 5 轮自然历史，记录实际长度；测第 6 轮，输出不超过 500 字 | 历史引用正确、上下文不混用 | 180s |

字数是请求约束，不是实测 Token 数；实际输出长度、Token、超长率必须报告，不能截断长回答来制造提速。Q4 预置历史使用正常授权路径，在计量前完成，其资源成本单列；本轮问题独立计时。

每案的 `case_id`、分类、合成输入/历史版本、期望数据范围、Skill/事实断言、答案数值和截止时间已固定在题库 JSON。执行时核对实际工具 schema 并适配自有 fixture 服务，不能把语义 fixture 直接当成已实现的 MCP 服务。涉及空气质量计算/等级时核对[领域参考](../domain/air-quality-level-reference.md)、当前 Skill 与实现，测试文档不自行补法规阈值。

低负载先验证场景确实走预期链路；Q2/Q3 未查数据而快速拒答，不能计为该类业务成功。自然语言细节可变化，路由/工具次数取实际值，不强行锁死优化后的实现。

### 3.2 状态与分母

- `N_planned`：计量期计划到达的新业务问题数；`N_sent`：实际发送数。发送差额、发压延迟和压测端瓶颈单列，不能悄悄降低负载。
- 一次新问题对应一个测试样本；`request_id`、`submission_id`、`attempt_id`、`platform_run_id` 分开保存。传输重试复用幂等键，不计为新成功；不确定受理结果先校准，禁止盲目重发。
- 普通性能轮默认不自动进行业务重试/重新生成；平台原有 SDK/工具重试策略冻结，记录每次物理尝试和消耗。恢复/重新生成/主动停止在独立场景测试，不混入普通负载分母。
- **完成成功**：客户端确认非空最终正文与完整结束，且服务端确认本次运行成功并建立可信回答关联，在截止时间内满足确定性业务断言。200、202、首 SSE、工具 HTTP 200 或仅服务端终态都不足以单独证明成功。
- 每个已发送问题归入一个主结果：`completed_success`、`business_failed`、`admission_failed`、`runtime_failed`、`client_timeout`、`transport_failed`、`cancelled`、`unknown`。按最早阻止本次按时成功的事实分类，保留后续服务端终态；超时后晚到成功不回填按时成功。
- 错误原因标签可多选，如 `provider_429`、`mcp_timeout`、`iam_unavailable`、`db_pool_wait`。模型重试后成功仍可属于完成成功，但限流/重试率不能抹去。
- 质量评价独立于技术完成：对已完整回答按冻结规则评分；另报 `质量合格完成数 / N_sent`，防止只对少量幸存答案打高分。

## 4. 指标字典

时长使用同一测量段的单调时钟；UTC 带时区墙钟用于关联，报告展示时区为 Asia/Shanghai。不同进程的单调值禁止相减。数据库时间须说明来源，收到回调的时间不能冒充实际执行时间。

| 指标/建议字段 | 定义与采集 | 汇总与边界 |
| --- | --- | --- |
| 接口首有效正文 `client_first_answer_ms` | 发压端提交前至解析到第一段可展示的答案正文；排除心跳、思考、工具、进度、元数据 | P50/P95、样本/缺失；不是 DOM 可见时间，不能在正文提取规则未确认时计算 |
| 浏览器首正文 `browser_first_visible_ms` | 同页面提交至实际首正文可见，复用浏览器计时语义 | P50/P95，独立浏览器样本与覆盖；不能从接口指标推算 |
| 完整回答 `client_complete_ms` / `browser_complete_ms` | 客户端提交至完整正文结束 / 浏览器显示完成，各自计时 | 主表显示按时成功样本 P50/P95，同时显示所有结果计数、超时及缺失；不得隐去失败造成的幸存偏差 |
| 服务耗时 `server_duration_ms` | 可信受理至实际终态；人工等待另列 | 和客户端、浏览器分开；不把不同端 P95 相减来估算网络耗时 |
| 成功吞吐量 | 计量窗口内完成成功的问题数 / 窗口分钟数 | 排空期完成另计；同报窗口进入量、完成量、期初/期末在途量及原始时间序列 |
| 完成成功率 | 本轮计量期发送问题中按时完成成功数 / `N_sent` | 按提交 cohort 在排空后判定；不可用完成窗口分子除提交窗口分母 |
| 错误/超时/限流比例 | 主结果数 / `N_sent`；另报遭遇过限流的问题数 / `N_sent`、429 物理尝试数 / 对应外呼尝试数 | 主结果互斥，原因可重叠；预期故障/拒绝另组，不混普通成功率 |
| 排队 `queue_wait_ms` / `queue_depth` | 对同一队列，用实际入队/开始处理事实计算；每秒采深度 | 逐队列 P50/P95、最大/末值/趋势；平台、观测 outbox 与客户端队列分开。受理至开始的近似值标 `admission_to_start_ms`，不能冒充纯排队 |
| 在途/负载 | 实际发送至客户端结束/截止的在途；服务端未终态另列 | 均值/峰值/时间序列；同时记录计划到达率、实际到达率和发压滞后 |
| CPU/内存 | 每秒采应用、BFF、IAM、数据库、依赖测试服务及压测端；同机虚拟机外层也采 | CPU 归一化到已分配核数的百分比；内存 RSS/容器用量定义保持一致，报均值/峰值/趋势和资源限额 |
| 数据库连接池 | 每个实际池的容量、占用、等待者、获取耗时/超时 | P95 等待、最大等待者、占用峰值；不把 PG 会话总数当应用池等待。拿不到时明确缺采集能力 |
| 模型/工具 | 每逻辑调用及物理尝试记录角色、耗时、状态、重试、关联 | 每问分布/总量、慢调用、失败来源；并行耗时不能简单相加后当作墙钟耗时 |
| 模型 TTFT | 每次模型尝试开始至首个可识别模型 Token | 按模型/角色/首片类型分组；正文、reasoning、tool call 区分；不是用户首正文 |
| Token/成本 | 提供商返回的去重 usage；按所有实际尝试和冻结价格版本计费 | 输入/输出/缓存/推理包含关系明确；未知为 null，报覆盖率；多币种分列，不重复加子集；每成功问题成本包含本轮失败消耗 |
| 质量 | 全部输出跑确定性事实/格式断言；每类固定案例在单请求与最高必测负载下各取 3 次评分 | 知识准确/数据范围/计算与单位/证据/多轮一致性五项，适用项均通过为合格；模型裁判仅作辅助，失败与争议需人工复核 |
| 隔离 | 同企业不同用户、跨企业、同用户 A→B→A，交错运行与连接复用 | 结果、历史、缓存、事件和工具请求分别核验；越权外呼看真实测试服务请求数 0，必须有有效正向控制 |

分位数统一使用线性插值：排序后位置 `(n-1)×p`，相邻值插值（与 `percentile_cont` 口径一致）；不平均各轮 P95。先逐轮、逐分类、逐负载统计，再按第 6 节作回归判定。可另列总体分布，但不得掩盖慢场景。

覆盖率的分母是该字段适用的样本数；字段不适用、提供商未提供、采集失败分开记录。样本不足 200 个的分组 P95 标探索性；P99 仅在分组至少 1,000 个有效样本时展示并注明样本量，不据此承诺稳定 SLA。失败样本保留实际观察时长、截止时间和缺失状态，不填“耗时 0”，也不将截止值假装完成耗时。

### 4.1 MCP 调用必须独立报告

MCP 是问答的外部执行链路，不能只报告整轮回答时间。按服务、工具、业务场景、负载与轮次分组；每条调用关联原问题。以下指标在报告中单列，未知为未采集，不因回答正确而推断调用成功。

| 指标 | 固定检查口径 |
| --- | --- |
| 首次连接与工具发现耗时 | 冷启动连接、初始化、tools/list分别记录；与已连接后的暖调用分开。多请求同作用域的发现是否去重、失败是否有界退避，跨企业不能共享凭据或授权结果 |
| 实际调用次数 | 每问逻辑调用、实际物理尝试、重试、重复执行分别统计；模型说“已查询”不是调用证据，须有执行端记录或测试服务请求计数 |
| 调用耗时P50/P95 | SDK发出至完整响应的同进程耗时，成功、失败、超时分组；工具首次返回字节可另测，不称模型TTFT。并行调用耗时不简单相加当回答总耗时 |
| 技术成功与业务有效 | 连接/协议/HTTP成功与业务结果分开；记录success=false、MCP isError、参数拒绝、权限拒绝、空数据、未知格式。普通有数据题须得到所需有效数据，空结果只在预期空结果的反例中合格 |
| 参数与结果正确性 | 核对真实调用的城市、日期、因子、统计周期、排名范围、站点类型与当前用户/企业；结果中字段/单位/数据时效与固定题断言相符，不能拿别题的缓存结果通过 |
| 超时、限流、重试 | 每工具问题受影响比例、物理尝试失败比例、429次数、重试原因/次数/等待分别报；即使重试成功也保留首次失败。超时按冻结截止处理，不无限重试 |
| 并发吞吐与积压 | 单位时间实际完成有效调用数、SDK/连接池等待、在途/队列、连接占用；MCP自身或受控服务达到上限时单列，不归咎模型或平台CPU |
| 返回体与处理开销 | 记录原始/交给模型的字节数或长度、截断/落库/摘要是否发生及耗时，摘要模型用量单列；不把正文写进普通日志。大结果不能因被截断而遗漏必要业务数据 |
| 故障与隔离 | 慢响应、断流、空数据、业务失败、撤权、凭据轮换、重复发现分别有正向控制；越权外呼实际增量必须为0，故障后连接/任务有界恢复 |

**通过规则**：普通受控fixture请求的必要参数/结果断言100%正确；越权、串数据及未解释重复执行为0；重试/超时不超冻结预算；逐工具暖调用P95使用第6节的连续指标比较规则。真实服务成功率、耗时和吞吐的绝对目标在profile中按工具冻结，不能把整轮问答成功率99%直接当作每个MCP的统一SLO。无逐工具目标或证据时该项未验收，不能仅凭HTTP200通过。

题库中的MCP期望来源见[固定参考题](basic-qa-reference-questions.md)；该表是测试检查要求，不表示本轮已执行真实MCP调用。首次连接、执行和结果加工都要采集；发现目录、schema可见、选中工具、真正发出请求和拿到有效数据是不同阶段。

## 5. 执行档位与步骤

### 5.1 标准档位

| 档位 | 场景及负载 | 执行要求 | 结论范围 |
| --- | --- | --- | --- |
| S 冒烟 | P/E 各 40 案各 1 次，单请求；浏览器每类至少 1 案 | 身份/关联/流式/终态/采集先跑通 | 仅可说冒烟通过，不可说性能回归通过 |
| R 版本回归 | P 层闭环并发 1、5、10；E 层闭环并发 1 和冻结基线并发 `C_ref`；每档 3 轮 | 每轮先预热至少 2 分钟且 8 个问题；随后计量至少 3 分钟且完整跑 40 案各 1 次，两个条件都满足再停止发压 | 同基线相同 R profile 比较，仅作小样本回归预警；不能据此承诺稳定尾延迟或可持续容量 |
| F 容量/发布回归 | R 全部；P/E 闭环探索 1、2、5、10、20、30，达边界即停；开放到达与突发、稳定性、故障/隔离 | 探索档每档至少 5 分钟且完整跑 40 案；`C_ref` 与候选边界达标档每档 3 轮，每轮至少 10 分钟且每类发送不少于 200 个；失败档保留已采样本，不强迫继续过载补数 | 当前部署在冻结问题集和资源下的已测容量；可持续容量必须有开放到达和长时证据 |

闭环并发指同时在途的独立问题，不是同时在线人数。每个模拟用户独立会话和企业上下文，每个并行问题独立对话；Q4 为各自预置历史。同一对话并发写入单独做冲突测试。

R 首次无 `C_ref` 时先做 F 建基线，并保存同次运行的 R profile 作为后续小样本比较对象。不得将 R 小样本分位数直接与 F 大样本分位数相比较。若仅准备做小样本回归，可独立登记 R 基线及其并发参照档，但不得登记 `λ_ref` 或称已完成容量验收。`C_ref=1` 时同一档不重复发压。

预算不足可以先跑 S 或部分档位，但报告必须标实际范围。F 的每类 200 要求针对发送数，实际成功分布不足时照实报告，不能为补足成功样本删除失败或只追加容易问题。预先估算至少需要的问题数、Token/费用和时长，在 manifest 中冻结预算；提前到限记中止及未满足项。以上时长均为下限，慢问答可能使采样持续更久。

### 5.2 固定到达率、稳定性和突发

1. 首轮从闭环成功吞吐量估计起点，在自有环境做开放到达探索；后续使用基线冻结的 `λ_ref`。依次测 `0.5/0.8/1.0/1.2 × λ_ref`，每档至少 15 分钟且每类发送不少于 200 个，重复 3 轮。`1.2×` 为超载探索，不要求普通 SLO 全过，但必须有界恢复。
2. 固定到达序列/随机种子，系统变慢也按计划产生新问题，记录计划/实际发送差、压测端等待/丢弃。压测端达到安全连接上限必须记未发出的负载，不能把削峰后的低到达率称为原档位通过。
3. `λ_ref` 下预热后计量至少 60 分钟。记录内存、连接、队列和未终态运行；不能只看开头/末尾截图。
4. 稳定到达 `λ_ref` 5 分钟后，提升至 `2×λ_ref` 60 秒，再回到 `λ_ref` 10 分钟。记录是否明确限流、积压、重复执行及恢复。突发区间单列，不混普通完成率。
5. 每档停止新发压后排空至少覆盖本档最长请求截止时间加 30 秒（v1 为 210 秒）；待处理/未知运行逐个校准。若服务端仍未终态，明确记录并用受支持停止入口处理，不能直接删库掩盖残留。

### 5.3 故障和隔离场景

在 P 层可控服务注入，禁止中断共享正式服务。每项至少 10 次，配有效正向控制及前后请求计数：

- 模型 429/超时、MCP 慢响应/业务失败：重试次数与配置一致、无无限重发、故障被正确分类，恢复后新问题能完成。
- IAM 不可用/运行中撤权：下一受保护步骤失败关闭；禁止新增越权模型/MCP 请求，实际请求增量为 0。
- 流断开/受理响应丢失：使用原幂等键校准，不重复执行；浏览器断流不冒充已取消。
- 主动停止：排队、处理、输出三阶段；请求停止不等于已确认取消，确认前不解除相关 UI 锁。
- 至少 2 企业、每企业 2 用户，主体/数据带合成唯一标记；跨用户/跨企业查询和 A→B→A 交错，合法请求能成功，非法数据与凭据不出现在答案、历史、事件或工具参数中。
- 观测服务故障：回答行为与业务授权边界维持，队列/重试有界，缺失与丢弃可见。

### 5.4 停止条件

安全/串数据/越权外呼、资源所有权不符立即停止。普通负载任一 60 秒窗口在至少 20 个已截止/结束问题中非成功比例超过 10%，或资源触及预设上限、压测端无法发出计划负载时，停止升压并留证。未到截止的问题不能提前归失败；故障注入和预期超载窗口独立判断。停止后仍须排空、校准、生成报告和只清理自有资源。

## 6. 基线与回归门禁

以下为 **v1 默认回归规则**，不是现用服务已达承诺。首轮执行前把有效阈值写入 manifest；修改阈值须先升策略版本并说明理由，不能测试失败后调宽来通过。

### 6.1 初次基线

无有效基线时只出 `BASELINE_CANDIDATE`（已测硬失败仍标 FAIL）。完成 F、质量/隔离核验及独立复核后，登记基线报告、比较键、每分类/档位的三轮原始值、`C_ref`、`λ_ref`、依赖配额及有效期。`C_ref` 为供后续复跑的并发档位；`λ_ref` 取重复开放测试中所有必测门禁达标、且通过 60 分钟稳定性验证的最高已测到达档位。未验证更高档位时写“至少达到”，不能称最大容量。仅完成 R 时可登记“R 小样本回归基线”，不登记容量。

首轮须在发压前确定每类业务可接受的**绝对首正文 P95、完成 P95**目标及预算，不能用一次很慢的结果反向定义合格。可先使用“Q1 首正文 5s、完成 30s”作为讨论起点，但必须在本轮 profile 中明确采用或替换；Q2–Q4 单独填，截止时间不等于可接受 P95。目标缺失时可探索、不能批准服务容量基线。

### 6.2 必测档位判定

| 门禁 | v1 默认规则 |
| --- | --- |
| 完整性 | 核心请求记录与发送数 100% 对账；同一请求/提交/运行关联可追溯；实际发压达到目标，样本/时长满足档位要求；不能存在未解释重复执行 |
| 成功率 | 普通 P 层每轮完成成功率 100%；普通 E 层每轮 ≥99%，且相对基线下降 ≤0.5 个百分点。全局与各分类分别检查；这是实测样本门禁，不是总体 99% 可用性统计证明 |
| 首正文/完成延迟 | 每分类、每必测档位：本轮 P95 不超过基线三轮 P95 的中位数加 `max(该中位数×20%, 200ms)`，同时满足 profile 的绝对目标。接口与浏览器分别比较；P50 诊断用；R 的小样本标记不能省略 |
| 吞吐量 | 闭环同并发逐轮成功吞吐不低于基线三轮吞吐中位数的 90%，按下文连续指标复测规则判定；开放 `λ_ref` 必须完成相同目标到达率且积压不持续增长。不能在不同到达率下用吞吐比直接判回归 |
| 排队与恢复 | `λ_ref` 计量最后 5 分钟的队列平均深度不高于最初 5 分钟均值加 `max(1, 初始均值×10%)`；入队/出队和在途对账。突发结束 10 分钟内队列及一分钟窗口首正文/完成 P95 回到基线同负载门禁范围；窗口不足 20 个完成样本标不足，延长恢复观察并记偏离 |
| 资源/连接 | 无 OOM、死锁、非预期连接池获取超时；60 分钟稳定性结束后排空，连接/活动任务回到暖机空闲范围；排空后 5 分钟内存均值较预热后空闲 5 分钟增长不超过 `max(10%, 100MiB)`，超出先判失败并定位缓存/泄漏，不能直接豁免 |
| 费用/调用 | 同问题组合每成功问题的 Token、同币种成本相对基线增幅 ≤20%；每问逻辑调用/物理尝试分布变化需解释。usage/价格缺失时只对完整覆盖子集比较并报告覆盖，不外推全量成本 |
| 质量 | 全部确定性关键事实/数据范围/数值/单位断言通过；评分样本合格率 ≥90%，且较基线下降 ≤2 个百分点。基础单请求不达标不能继续宣称高并发通过；同一冻结质量样本跨低/高负载配对复核 |
| 安全与隔离 | 所有正反例通过；串数据、越权外呼、凭据泄露、停止/撤销后越界执行均为 0，任意一例即失败，不用平均正确率抵消 |

延迟等连续指标先逐轮统计，三轮中至少两轮越过同一门禁即为确认回归；只有一轮越过时，不判 PASS，固定条件补跑三轮，合并六轮至少两轮越界则 FAIL，否则记录波动后评审。成功率、安全、质量关键断言、数据完整性和资源硬错误任一轮不满足即 FAIL。不能只选最好一轮、事后删离群点或以 P95 的平均数作为比较值。

资源 CPU/池占用高本身是诊断信号；不设置脱离资源配置的统一 CPU 百分比上限。真正门禁是响应、排队、资源硬错误与恢复。内存规则按同一采集定义执行；持续有界缓存也需在首次基线前说明容量，不能把未解释增长认作正常。

核心计时、队列/池等待、终态/隔离证据缺失导致门禁无法判断时，该范围为 `BLOCKED`，不得记 PASS。提供商明确不提供的 Token/价格可登记为“不可测限制”，不编造数值；性能结论可限于其他已测门禁，但必须写“成本未验收”，不能称八类指标全部通过。接口回归可以独立出结论；未执行浏览器时写“浏览器体验未验收”，不得用接口时间替代。

门禁按档位适用：R 必测请求/发压完整性、成功率、接口延迟/吞吐、可采集的调用/资源/用量、全量确定性断言；每次仍执行至少一组带正向控制的跨用户/跨企业交错反例。60 分钟内存、开放到达、完整故障矩阵及高低负载质量配对属于 F；R 未执行这些项写“不在本次档位范围”，不能把它们标通过。安全失败在任意档位均立即 FAIL。F 的浏览器默认每类每案在单请求和 `C_ref` 背景负载下各 3 次，报告其独立样本及限制；若要承诺整档浏览器容量，须另设足量浏览器并发 profile。

### 6.3 报告结论

- `PASS`：本次声明范围内必测门禁均通过，与已批准基线可比；列出范围及未覆盖部分。
- `FAIL`：至少一项已测门禁失败；独立列已确认问题及证据。
- `BLOCKED`：环境、样本、工具或核心采集不满足，无法完成该范围；已测失败仍保留为 FAIL，不能被 BLOCKED 隐藏。
- `INCOMPARABLE`：比较条件发生变化，不给相对回归通过结论；绝对目标与安全失败仍单列。
- `BASELINE_CANDIDATE`：首轮候选，等待完整证据及复核登记；不能当上线容量承诺。

各层/档位/浏览器/成本/安全独立给状态，总结保留最严重已知失败。报告的 PASS 必须带范围；S 档仅“冒烟 PASS”。基线更新不覆盖旧结果，优化或升级后使用新 run_id，重新执行相应门禁。

## 7. 报告与可复核数据

每轮新建 `docs/reviews/basic-qa-performance/<run_id>/`；`run_id` 使用北京时间 `YYYYMMDD-HHmmss-<short-id>`，禁止覆盖历史报告。敏感正文及较大原始流放受保护本机证据目录，报告只引用受限路径、摘要和保留期；不得为了留证提交秘密或大文件。

```text
<run_id>/
  report.md                    # 从报告模板复制；人工复核后定稿
  manifest.json                # 冻结环境、输入、profile、阈值、来源摘要
  summary.json                 # 机器可读汇总、覆盖与逐项判定
  requests.jsonl               # 每个计划问题一行，未发出也保留
  calls.jsonl                  # 每次模型/工具物理尝试及逻辑调用关联
  resources.jsonl              # 每秒资源、池、队列、压测端序列
  checks.jsonl                 # 质量/隔离/故障断言与证据引用
  browser.jsonl                # 真实浏览器测量；未执行则清单明确缺失
  evidence-index.json          # 文件摘要、受限原始证据引用、覆盖/缺失说明
```

最小字段约定（后续压测器/报告生成器必须遵循；不是当前已存在的命令）：

| 文件 | 必需字段 |
| --- | --- |
| 通用 | `schema_version=basic-qa-perf.v1`、`run_id`、`round_id`、`layer`、`profile`、`stage`、`recorded_at`（UTC 带时区）；不适用字段显式 null 及原因 |
| manifest | 第 2 节冻结项、每类绝对目标/截止、预算、基线标识、比较键、随机种子、测试代码/数据摘要、资源所有权、实际验证及清理记录 |
| requests | `sample_id/case_id/category`、主体别名、计划与实际发送时间/差、提交/请求/attempt/run/answer 的独立 ID、计时指标、主结果/原因、截止/观察时长、晚到服务端终态、各字段采集状态 |
| calls | `sample_id`、逻辑调用/观测 ID、`kind/role/model/service`、物理尝试序号、起止/耗时/TTFT/首片类型、状态/原因、usage/缺失、价格版本/币种/成本 |
| resources | 组件及实例 ID、采样时间、CPU 定义及限额、内存定义及用量、池容量/占用/等待/超时、队列名称/深度、客户端和服务端在途/发压延迟；缺失显式标注 |
| checks | `check_id/sample_id`、检查类别、期望/实际脱敏摘要、`PASS/FAIL/BLOCKED`、正向控制、证据引用；断言规则版本 |
| browser | `sample_id/measurement_id`、浏览器/版本/视口、独立浏览器负载、首正文/完成时长、来源/缺失、关联验证。低并发抽查不能证明整档浏览器并发容量 |
| summary | 每层/分类/档位/轮次/来源的计划/发送/各结果/限流数、样本/缺失/分布、吞吐与窗口、覆盖、基线值/门禁/差值/状态/原因；字段为 null 时有缺失原因，禁止以 0 代替未知 |

统计必须从本轮原始明细重新生成，不手填“实测值”。报告生成失败时仍保留原始数据并生成失败说明；未实现自动化时人工整理也须能逐项追溯，不能只有截图和结论。先验证计划/发送/结果计数守恒、幂等去重、Token 子集不重复、费用覆盖与分位数算法，再生成对比。

## 8. 回归频率与交付检查

| 触发 | 至少执行 |
| --- | --- |
| 文档修改 | 链接、口径与模板一致性；不机械跑长压测 |
| 普通 basic QA 节点、提示词、Skill、流式或观测改动 | S + R；涉及语义变化更新质量配对证据，冻结旧集不改答案迁就实现 |
| 模型/依赖/重试/连接池、IAM、受理、缓存、持久化、共享工具链路改动，或发布容量承诺 | F；环境改变时先做可比性判断，必要时建立新基线 |
| 修复失败 | 新 run_id，在同负载复现原失败并验证修复，再覆盖受影响相邻档位；保留原报告 |

执行者逐项完成：冻结来源与所有权 → 校验观测 → S → 规定负载/质量/隔离 → 排空校准 → 汇总报告 → 独立复核 → 回收自有资源。实施者自述、复用旧分数、HTTP 200、现有测试全绿均不能替代本轮负载证据。

本次交付仅建立规范和报告模板。后续若实现自动化，应让发压、采集、汇总和报告生成共用上述 profile 与 schema；任何无法采集的项先报告缺口，不自动补成通过。
