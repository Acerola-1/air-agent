## 一、2026 RAG 技术要求汇总

### 1.1 核心知识地图(七层 RAG 全链路)

```
┌─────────────────────────────────────────────────────────────┐
│  离线索引阶段:文档 → 解析 → 切分 → Embedding → 向量库 + 关键词索引 │
├─────────────────────────────────────────────────────────────┤
│  在线查询阶段:                                              │
│    Query → 查询改写 → 多路召回 → 融合 → Rerank → 上下文组装 → LLM 生成 → 引用溯源 │
└─────────────────────────────────────────────────────────────┘
```

每层都有"幼儿园版本"和"工业级版本"之分,面试官考察的就是两者之间的鸿沟。

### 1.2 各层技术要求矩阵

| 层级 | 幼儿园版本(不及格) | 工业级版本(达标) | 进阶版本(加分) |
|---|---|---|---|
| **文档解析** | PyPDFLoader 一把梭 | 数字 PDF / 扫描 PDF 分流,表格转 Markdown,布局感知解析 | 多 OCR 引擎投票,置信度阈值控制 |
| **切分策略** | 固定 512 token 硬切 | 递归字符切分 + overlap 10-20% | 语义切分 / Parent-Child / Small-to-Big |
| **Embedding** | ada-002 默认 | 按语言/领域选型,中文用 BGE/M3E,医疗用 BioBERT | Embedding 微调,维度/上下文长度权衡 |
| **向量库** | Chroma 跑 demo | 按规模选型:FAISS/Milvus/Qdrant/pgvector | HNSW vs IVF 参数调优,增量索引 |
| **查询改写** | 不做 | Query Rewriting 规范化口语 | HyDE / Multi-Query / Sub-Question 分解 |
| **检索** | 纯向量 Top-K | **混合检索(向量 + BM25)** | 元数据过滤,动态 Top-K,先分类再检索 |
| **融合** | 分数加权平均 | **RRF(倒数排名融合)** | Learning to Rank,动态权重 |
| **Rerank** | 不做 | Cross-Encoder 精排(BGE-Reranker/Cohere Rerank) | 检索 Top-50 → Rerank → Top-5 |
| **上下文组装** | 全塞进 prompt | 上下文压缩(LLMLingua),Lost in the Middle 规避 | 动态截断,引用编号 |
| **生成** | 默认 prompt | 系统约束 + temperature=0 + 引用要求 | 引用溯源,faithfulness 校验 |
| **评估** | 无 | **RAGAS 四指标**(Faithfulness/Answer Relevancy/Context Precision/Context Recall) | LLM-as-Judge + Golden Set + A/B |
| **生产化** | 单机 demo | 多租户隔离,缓存,延迟预算,P95 监控 | 增量索引 CDC,降级,成本管控 |
| **进阶范式** | — | Self-RAG / CRAG | Graph RAG / Agentic RAG |

### 1.3 关键数值(面试必背)

| 指标 | 推荐值 | 理由 |
|---|---|---|
| Chunk size | QA 场景 256-512 token,长文综合 1024-2048 | 太小丢上下文,太大稀释相似度 |
| Overlap | 10-20%(如 512 chunk 配 50-100 overlap) | 避免边界信息切断 |
| 向量检索 Top-K | 10-20(给 Rerank 留余量) | Rerank 后取 Top-5 |
| Rerank 输入 | Top-50 → 输出 Top-5 | Cross-Encoder 慢,只对小候选集 |
| RRF k 参数 | 60(行业默认) | 平衡头部与尾部排名影响 |
| 相似度阈值 | 0.55-0.65 | 低于阈值视为召回失败 |
| Faithfulness 红线 | 0.90(低于阻断上线) | 临床/企业级硬指标 |
| Embedding 维度 | 768-1536 | 越高表达越强但成本越高 |
| 缓存 TTL | 1 小时(query+chunk_ids hash) | 平衡新鲜度与命中率 |
| P95 延迟预算 | embedding 20ms + HNSW 5ms + LLM 1-3s | LLM 是瓶颈,流式+压缩 |

### 1.5 arXiv 2026.04 实测数据(面试可引用)

> 覆盖 23088 条真实查询的论文数据:
> - 纯向量检索 Recall@5 = 58.7%
> - 双路 RRF 融合 = 69.5%(+10.8pp)
> - RRF + Reranker = 81.6%(+17.4pp)
>
> 结论:**多路召回 + Rerank 是生产级 RAG 标配,能把召回率从 60% 干到 85%**。

## 二、25 道 RAG 高频面试题

> 每题结构:**题目 → 面试官追问点 → 标准答案 → 加分点 → 避坑指南**。标注【高频】的为字节/阿里/Cohere 等多次考察的题目。

### A. 基础概念(必答,60 秒内讲清楚)

#### Q1:什么是 RAG?它解决了大模型的哪些痛点?【必考】

**面试官追问**:为什么不让 LLM 直接回答?LLM 的知识截止问题你怎么解决?

**标准答案**:
RAG(Retrieval-Augmented Generation,检索增强生成)是在 LLM 生成答案前,先从外部知识库检索相关信息,把检索结果和问题一起喂给 LLM,让它基于真实资料回答。

解决三大痛点:
1. **知识时效性**:LLM 训练数据有截止日期,RAG 通过外部知识库提供"实时"补充,比重新训练成本低几个数量级。
2. **幻觉问题**:LLM 容易"一本正经地胡说八道",RAG 让它基于检索到的事实回答,可溯源。
3. **私有数据无法触达**:企业内部文档/客户数据 LLM 没见过,RAG 接入私有知识库。

**加分点**:强调 RAG 不是替代 LLM,是给它补外部知识;LLM 负责理解和生成,RAG 负责提供事实依据。

**避坑**:不要只说"检索+生成",必须补充核心作用;不要和微调混淆。

#### Q2:RAG 和微调(Fine-tuning)有什么区别?什么时候用哪个?【高频】

**面试官追问**:你的项目里用的是 RAG 还是微调?为什么?

**标准答案**:

| 维度 | RAG | 微调 |
|---|---|---|
| 知识存储位置 | 外部知识库(向量库) | 模型参数里 |
| 落地成本 | 低,无需标注数据和 GPU | 高,需大量标注数据 + GPU |
| 更新效率 | 改向量库即可,分钟级生效 | 需重新训练,周期长 |
| 可解释性 | 可溯源到具体文档 | 黑盒 |
| 擅长场景 | 知识频繁变动、需审计 | 固定领域深度优化、风格学习 |

**选择原则**:
- 知识频繁更新 → RAG
- 需要特定语言风格/指令遵循 → 微调
- **生产实践:RAG + 微调组合拳**——微调让模型学会领域术语和风格,RAG 提供实时知识。

**加分点**:举医疗例子——微调让模型学会医学术语和诊断格式,推理时用 RAG 挂载最新病例和药品数据。

#### Q3:RAG 的完整工作流程是什么?【必考】

**面试官追问**:能完整讲一下从用户提问到最终回答的链路吗?

**标准答案(七步链路)**:
```
Query → 文档处理 → Chunking → Embedding → 检索 → Rerank → 生成
```

**离线索引阶段**:
1. 文档解析:PDF/Word/Markdown 提取文本,扫描版走 OCR,表格转 Markdown。
2. 切分:长文档切成语义连贯的 chunk。
3. Embedding:每个 chunk 转向量。
4. 存储:向量 + 元数据存入向量库,可选建关键词索引。

**在线查询阶段**:
5. 查询预处理:清洗、改写、补全。
6. 检索:向量召回 Top-K(可选混合检索)。
7. Rerank:Cross-Encoder 精排。
8. 生成:检索结果 + 问题拼 Prompt 喂 LLM,带引用。

**加分点**:不要只背步骤,要说清楚每步的关键决策点——"我为什么选 Milvus 不选 FAISS,Top-K 为什么设 5 不是 10"。

### B. 切分与索引

#### Q4:Chunk 策略怎么选?不同策略的 trade-off 是什么?【高频】

**面试官追问**:chunk size 怎么定?overlap 有啥用?切大了切小了各有什么问题?

**标准答案(五种策略)**:

| 策略 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 固定大小切分 | 按 Token 硬切 | 实现简单 | 语义边界全破坏 | 基本不用 |
| 递归字符切分 | 按分隔符优先级递归(段落→换行→句号) | 工程最常用 baseline | 仍可能切断语义 | 通用首选 |
| 语义切分 | 相邻句算 embedding 余弦相似度,断点处切 | 语义完整性最好 | 计算成本高 | 高质量场景 |
| **Small-to-Big / Parent-Child** | 小 chunk 检索,返回父级大 chunk 给 LLM | 检索准 + 生成上下文完整 | 索引结构复杂 | **强烈推荐** |
| 层级切分 | 三层(文档/段落/句子),不同粒度不同用途 | 灵活 | 实现复杂 | 大型知识库 |

**size 选择**:
- QA 场景:256-512 token,overlap 50-100(10-20%)
- 长文综合:1024-2048 token

**切大切小问题**:
- 切太大:相似度稀释,检索不准,浪费 context
- 切太小:语义不完整,LLM 看不懂半句话

**加分点**:Parent-Child 是最值得讲的——检索用小 chunk(粒度细、语义准),生成用大 chunk(上下文完整),两不误。

#### Q5:你的 RAG 系统固定 512 token 切分,用户反馈答案经常缺失重要上下文,怎么回事?怎么修?【Anthropic/Cohere 真题】

**面试官追问**:为什么不直接增大 chunk size?

**标准答案**:
**根因**:固定大小切分没有 overlap,答案横跨两个相邻 chunk 时,任一 chunk 单独都不完整,永远检索不到完整答案。

**修复方案(递进)**:
1. **加 overlap**(10-20%):让相邻 chunk 有重叠,避免边界信息切断。
2. **改用递归字符切分**:按段落/句号等语义边界切,而非任意 token 数。
3. **Parent-Child**:小 chunk 检索,命中后返回父级大 chunk,保证上下文完整。
4. **召回相邻 chunk**:检索到某 chunk 时,自动带上前后相邻 chunk。

**为什么不直接增大 size**:chunk 越大,相似度计算越稀释,检索准确率反而下降;且浪费 context window。

### C. Embedding 与向量库

#### Q6:Embedding 模型选型要考虑哪些因素?中文场景选什么?【高频】

**面试官追问**:你怎么评估 Embedding 模型效果?

**标准答案(四因素)**:
1. **语言支持**:中文用 BGE/M3E/Text2Vec,英文用 OpenAI text-embedding-3/Cohere embed-v3。
2. **向量维度**:768/1024/1536,越高表达越强但成本越高。
3. **上下文长度**:要覆盖 chunk size,常见 512/1024/2048/8192。
4. **性能指标**:MTEB/C-MTEB 评测集上的 MRR/NDCG/Recall@K。

**中文首选**:BGE-large-zh(MTEB 中文榜单领先)、M3E-large、GTE-large-zh。

**评估方法**:
- 公开评测集:C-MTEB(中文)、MTEB(英文)。
- 业务数据:构建自己的测试集,算检索准确率和召回率。

**加分点**:提"先开源验证效果,不达标再商用 API"的工程思路。

#### Q7:向量数据库怎么选?Milvus/FAISS/Qdrant/pgvector 各自适合什么场景?【高频】

**面试官追问**:HNSW 和 IVF 索引区别?

**标准答案**:

| 向量库 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|
| **FAISS** | Facebook 开源,索引算法丰富,快 | 不支持分布式和持久化 | 小规模本地部署/demo |
| **Milvus** | 分布式,多索引,混合查询 | 运维复杂 | 大规模生产环境 |
| **Qdrant** | Rust 实现,性能好,过滤强 | 生态较小 | 中规模生产 |
| **pgvector** | 复用 PG 运维,SQL 友好 | 性能不如专用库 | 已有 PG 基础设施 |
| **Pinecone** | 托管,开箱即用 | 成本高 | 快速验证 |
| **Chroma** | 轻量,Python 友好 | 不适合大规模 | 原型/小项目 |
| **Elasticsearch** | 同时支持关键词+向量 | 向量性能不如专用库 | 混合检索场景 |

**HNSW vs IVF**:
- **HNSW**:基于图结构,构建慢但查询快,适合静态数据。
- **IVF**:基于倒排文件,构建快但查询稍慢,适合动态更新。

#### Q8:你升级 Embedding 模型(ada-002 → text-embedding-3-large),上线后搜索崩了,维度不匹配,怎么回事?怎么修?【Anthropic 真题】

**标准答案**:
**根因**:不同 Embedding 模型向量维度不同(ada-002 是 1536 维,text-embedding-3-large 是 3072 维),且向量空间完全不同,**新旧模型的向量不可比较**。

**修复方案(三选一)**:
1. **全量重新 Embedding(推荐)**:用新模型把所有文档重新向量化,重建索引。耗时但最干净。
2. **双索引并行 + 灰度切换**:新模型建新索引,流量灰度从旧切到新,全量切换后下线旧索引。零停机但需双倍存储。
3. **维度对齐(不推荐)**:用降维投影把新向量映射到旧维度,但向量空间不同,相似度失真。

**加分点**:强调"换 Embedding 模型 = 换向量空间,必须全量重建",这是常见坑。

### D. 检索与融合

#### Q9:纯向量检索有什么问题?为什么需要混合检索?【高频】

**面试官追问**:向量检索和关键词检索什么区别?

**标准答案**:
**向量检索(稠密)的盲区**:
- 学的是语义相似度,不擅长精确匹配。
- 用户问"GPT-4o 的 context window 是多少",可能召回一堆"大模型能力"文档,漏掉精确包含数字的那段。
- 产品型号/版本号/代码方法名/财务数字场景灾难性。

**BM25(稀疏)的盲区**:
- 只认字面词,不懂语义。
- 用户说"退货",文档写"申请售后",词不重叠就召不回。
- 口语化提问抓瞎。

**混合检索**:两路并行,向量负责语义泛化,BM25 负责精确匹配,互补盲区。

**对照表**:

| 查询类型 | 向量检索 | BM25 |
|---|---|---|
| 语义问答 | ✅ 优秀 | ⚠️ 依赖关键词 |
| 同义词泛化 | ✅ 优秀 | ❌ 词不重叠则失败 |
| 精确专有名词 | ⚠️ 一般 | ✅ 优秀 |
| 产品型号/版本号 | ❌ 较差 | ✅ 优秀 |
| 财务数字 | ❌ 较差 | ✅ 优秀 |

#### Q10:多路召回结果怎么融合?RRF 算法原理是什么?为什么不能直接分数加权?【字节高频】

**面试官追问**:RRF 的 k 参数为啥取 60?

**标准答案**:
**不能直接加权的原因**:不同路线的分数不在同一量纲——向量相似度是 0~1 浮点数,BM25 分数可能是几十甚至上百,直接相加向量贡献被淹没。即使归一化,换语料又要重调参数。

**RRF(Reciprocal Rank Fusion,倒数排名融合)**:
```
score = Σ 1 / (k + rank_i)
```
- `rank_i` 是文档在第 i 路召回中的排名(从 1 开始)。
- `k` 是平滑参数,典型取 60。
- **核心思想**:不看绝对分数,只看相对排名,把不同路线的排名"翻译"成同一种语言。

**k=60 的理由**:平衡头部(rank=1 的文档得分 1/61)与尾部(rank=100 的文档得分 1/160)的影响,避免头部独大,给中尾部文档合理权重。行业经验值,实测稳定。

**其他融合方案**:
- **加权融合**:向量 0.7 + 关键词 0.3,简单可控,中小规模首选。
- **Learning to Rank**:训练 LambdaMART/XGBoost 学习动态权重,效果最好但需标注数据。

#### Q11:什么是 Rerank?为什么混合检索之后还要重排序?【必考】

**面试官追问**:Bi-Encoder 和 Cross-Encoder 区别?为啥 Rerank 精度更高?

**标准答案**:
**Rerank 的必要性**:向量检索用 Bi-Encoder(query 和 doc 分别编码再算相似度),速度快但精度有限,召回的 Top-K 里混有"主题相关但不答问题"的噪声。Rerank 用 Cross-Encoder 做 query-doc 深度交互,精度提升一个量级。

**Bi-Encoder vs Cross-Encoder**:

| 维度 | Bi-Encoder(召回) | Cross-Encoder(Rerank) |
|---|---|---|
| 架构 | query 和 doc 分别编码,余弦相似度 | query 和 doc 拼接输入,联合编码 |
| 交互 | 无交互(双塔) | 深度交互(cross-attention) |
| 速度 | 快,可离线预计算 doc 向量 | 慢,每次 query-doc 对都要推理 |
| 精度 | 一般 | 高 |
| 用途 | 大规模召回 | 小候选集精排 |

**标准流程**:召回 Top-50 → Rerank → Top-5。

**常用模型**:BGE-Reranker、Cohere Rerank、Voyage Rerank、bge-reranker-large。

**实测数据**:加入精排后,答案准确率从约 65% 提升至 85%+。

#### Q12:什么是 HyDE?为什么用假设文档向量检索比直接用问题向量效果好?【高频】

**面试官追问**:HyDE 生成的假想答案内容是错的怎么办?

**标准答案**:
**HyDE(Hypothetical Document Embeddings)**:不让 LLM 直接回答问题,而是让它先"凭空生成"一段假想答案文档,用这段假想文档的向量去检索真实知识库。

**为什么有效**:
- 用户问题是"提问体"(疑问句),文档是"陈述体",表述风格差异大,Embedding 模型难捕捉关联。
- 假想答案是"陈述体",和真实文档风格一致,**把查询从"问题空间"映射到"文档空间"**,跨越语义鸿沟。

**内容错了怎么办**:
- 我们要的不是假想答案的**内容正确性**,而是它的**语义方向**——它帮我们找到正确文档,真正答案由检索到的真实文档提供。
- 即使假想答案有事实错误,只要语义方向对,检索结果就是对的。

**对比 Multi-Query**:Multi-Query 是生成多个变体查询(同语义不同表达),HyDE 是生成假想答案(跨空间映射),两者可组合。

#### Q13:Lost in the Middle 是什么现象?对 RAG 有什么影响?怎么应对?【字节】

**标准答案**:
**现象**:LLM 对长 context 的注意力呈"U 型"——开头和结尾的信息关注度高,中间信息容易被忽略。即使相关文档被检索到,如果放在 context 中间,LLM 也可能"视而不见"。

**影响**:RAG 把检索到的多个 chunk 拼进 prompt,如果相关 chunk 恰好排在中间,答案质量下降。

**应对方案**:
1. **减少 context 数量**:Rerank 后只取 Top-3-5,不要贪多。
2. **重排顺序**:把最相关的 chunk 放在 context 开头和结尾,中间放次相关。
3. **上下文压缩**:用 LLMLingua 等工具压缩无关内容,缩短 context 长度。
4. **LongReorder**:按相关度从高到低排列,把最相关的放两端。

### E. 查询优化

#### Q14:查询改写(Query Rewriting)有哪些策略?分别解决什么问题?【高频】

**面试官追问**:Multi-Query 和 Step-Back Prompting 分别解决什么问题?

**标准答案(四种策略)**:

| 策略 | 原理 | 解决问题 |
|---|---|---|
| **Query Rewriting** | LLM 把口语化问题改写成规范检索式 | "transformer 那个注意力的东西怎么算" → "Transformer Self-Attention 计算过程" |
| **HyDE** | 生成假想答案文档,用文档向量检索 | 跨越"问题空间"到"文档空间"的语义鸿沟 |
| **Multi-Query** | 生成 3-5 个变体查询,分别检索后合并去重 | 同一意图多种表达,提升召回率 |
| **Sub-Question Decomposition** | 复杂问题拆成多个子问题分别检索 | "对比 GPT-4 和 Claude 代码生成" → 两个子问题分别检索 |

**Step-Back Prompting**:让 LLM 先把具体问题"后退"到更抽象的概念问题,先检索抽象概念,再回答具体问题。适合需要背景知识的问题。

**加分点**:提"动态 Top-K"——简单问题召回 20 篇,复杂多跳问题召回 100 篇,根据问题复杂度自适应。

### F. 评估与质量

#### Q15:如何评估 RAG 系统的质量?RAGAS 四个指标分别怎么算?【必考】

**面试官追问**:Faithfulness 0.91、Context Relevance 0.88,但用户说 1/5 答案不对,问题出在哪?【Anthropic/Cohere/Perplexity 真题】

**标准答案**:
**RAGAS 四指标**:

| 指标 | 含义 | 计算方式 |
|---|---|---|
| **Faithfulness(忠实度)** | 答案是否基于检索到的 context,有无幻觉 | 把答案拆成 claims,逐个判断是否能在 context 找到支撑,可支撑比例 |
| **Answer Relevancy(答案相关性)** | 答案是否真正回答了用户问题 | 从答案反推可能的问题,与原问题的语义相似度 |
| **Context Precision(上下文精确率)** | 检索到的 context 里有多少是真正相关的 | 相关 chunk 数 / 总检索 chunk 数 |
| **Context Recall(上下文召回率)** | 回答问题所需的 context 是否都被检索到 | 被检索到的相关 chunk / 知识库中所有相关 chunk |

**关键区别**:
- Faithfulness 管"答案有没有幻觉"
- Context Relevance 管"检索的文档相不相关"
- **Answer Relevancy 管"答案有没有回答问题"** ← 这是 Anthropic 真题的答案

**真题解答**:Faithfulness 和 Context Relevance 都高,说明答案基于 context 且 context 相关,但用户觉得不对,问题在 **Answer Relevancy 低**——检索到的文档主题相关但不包含具体答案信息。通常根因是切分问题(相关句子在没被检索到的 chunk 里)或 Embedding 问题(捕捉了主题相似而非答案相似)。

#### Q16:如何避免 RAG 的幻觉?【高频】

**面试官追问**:Prompt 约束为啥不够,还需要什么机制?

**标准答案(五层防御)**:
1. **RAG 增强**:让模型基于检索到的真实内容生成,而非依赖训练记忆。最根本手段。
2. **Prompt 约束**:"ONLY use information from the CONTEXT below. If not in CONTEXT, say 'I don't know'." 明确禁止编造。
3. **temperature=0**:减少创造性生成,降低幻觉概率。
4. **输出校验**:用 fast LLM judge 检查答案每个 claim 是否在 context 中,标记不存在的 claim。
5. **引用溯源**:每个答案必须标注来源 chunk,用户可核对,违规可见。

**Prompt 约束不够的原因**:LLM 仍可能在 context 不完整时"脑补"缺失部分,需要校验层和引用层兜底。

**加分点**:提"Faithfulness CI 红线"——任何改动让 Faithfulness 低于 0.90 阻断上线。

#### Q17:RAG 检索效果不好怎么优化?【字节,系统题】

**面试官追问**:沿着一条查询从用户提出到最终送进 LLM 的完整链路,每个环节怎么拆解瓶颈?

**标准答案(四维度拆解)**:

**1. 查询侧优化**:
- Query Rewriting:规范化口语化问题。
- HyDE:跨语义鸿沟。
- Multi-Query:多变体提升召回。

**2. 索引侧优化**:
- 切分策略:Parent-Child / 语义切分。
- Embedding 微调:领域适配。
- 元数据:加标签辅助过滤。

**3. 检索侧优化**:
- 混合检索:向量 + BM25。
- 动态 Top-K:简单问题少召回,复杂问题多召回。
- 元数据过滤:先按类别/时间缩小范围。

**4. 后处理侧优化**:
- Rerank:Cross-Encoder 精排。
- 上下文压缩:LLMLingua。
- Lost in the Middle 规避。

**加分点**:不要散点列举,要沿链路拆解,体现体系化认知。

### G. 进阶范式

#### Q18:Self-RAG 和 CRAG 是什么?和传统 RAG 有什么区别?【高频】

**面试官追问**:为什么要让模型自己决定要不要检索?

**标准答案**:

| 范式 | 核心思想 | 区别 |
|---|---|---|
| **传统 RAG** | 每个问题都检索,固定流程 | 无脑检索,简单问题也走全链路,浪费 |
| **Self-RAG** | 模型自己决定**要不要检索**、检索结果**相不相关**、答案**要不要基于检索** | 训练模型输出反思 token(retrieve/no-retrieve, relevant/irrelevant, supported/not-supported),按需检索 |
| **CRAG(Corrective RAG)** | 检索后**评估质量**,质量差时触发纠正(重新检索 / 网页搜索 / 用原始知识) | 检索评估器打分,低分走 web search 兜底 |

**为什么要让模型决定**:
- 简单问候("你好")不需要检索,无脑检索浪费成本。
- 检索到的文档不相关时,硬塞进 prompt 反而引入噪声,不如不检索。
- 模型对自己答案的置信度有判断,低置信才检索。

#### Q19:Graph RAG 和传统 RAG 有什么区别?【高频】

**面试官追问**:Graph RAG 为什么比传统 RAG 强?

**标准答案**:
**传统 RAG 的局限**:基于向量相似度,只能找"语义相近"的文档,无法处理**关系推理**。比如"A 是 B 的父亲,B 是 C 的父亲",问"A 和 C 什么关系",向量检索找不到。

**Graph RAG**:
- 构建**知识图谱**:从文档抽取实体和关系,存入图数据库。
- 检索时**图遍历**:找到实体后,沿关系边遍历,获取关联信息。
- 适合多跳推理、关系查询、全局摘要。

**优势**:
1. 关系推理:向量检索搞不定的"A 和 C 什么关系",Graph RAG 通过两跳遍历解决。
2. 全局视角:传统 RAG 是局部检索,Graph RAG 可做全局摘要(社区检测 + 层级摘要)。
3. 可解释性:关系链路可追溯。

**代价**:图谱构建成本高(实体抽取 + 关系抽取 + 图维护),适合关系密集的领域(医疗/法律/金融)。

#### Q20:Agentic RAG 是什么?和普通 RAG 有什么区别?【高频】

**标准答案**:
**Agentic RAG**:让 Agent 自主决定检索策略,根据查询复杂度动态调整检索轮次和方式。

**与普通 RAG 的区别**:

| 维度 | 普通 RAG | Agentic RAG |
|---|---|---|
| 检索次数 | 固定 1 次 | 按需多轮,可迭代 |
| 检索策略 | 固定向量+BM25 | 动态选择(向量/BM25/图/网页) |
| 决策权 | 开发者预设 | Agent 自主决策 |
| 复杂问题 | 单次检索不够就答不好 | 多跳检索,逐步细化 |

**适用场景**:
- 多跳推理("对比 X 和 Y 在 Z 场景的表现")
- 需要补充检索("先查 X,根据 X 结果再查 Y")
- 复杂分析(报告生成、深度研究)

**加分点**:结合你的 air_agent 项目——你的 `deep-research` graph 本质就是 Agentic RAG,Agent 自主决定检索策略和轮次。

### H. 生产与工程

#### Q21:如何构建生产级 RAG 系统?【系统设计题】

**面试官追问**:多租户怎么做?延迟怎么优化?成本怎么控?

**标准答案(生产级五要素)**:

**1. 多租户隔离**:
- 每个租户独立 collection / namespace。
- 元数据过滤:`tenant_id` 字段前置过滤。
- 权限:不同租户只能查自己的数据。

**2. 延迟优化**:
- 流式生成:返回 partial response,用户感知延迟大幅降低。
- 上下文压缩:LLMLingua 压缩 50-70%,缩短生成时间。
- 小模型分流:简单问题用小模型判断是否需要检索,跳过检索。
- 缓存:query + top-3 chunk_ids hash,Redis 缓存 1 小时 TTL。

**3. 成本管控**:
- Embedding 缓存:同一文档不重复 embed。
- 小模型 Rerank:用轻量 Cross-Encoder。
- 监控 token 消耗,设置预算告警。

**4. 增量索引**:
- 文档 content hash,更新时只重新 embed 变化的文档。
- 软删除:`superseded=True` + timestamp,保留审计,不硬删。
- CDC 管道:源系统 webhook 触发索引更新,近实时。

**5. 监控**:
- 每次查询记录:query + 检索 chunks + 答案 + Faithfulness。
- 夜间采样跑 Faithfulness,低于 0.90 告警。
- 检索 max-similarity 低于 0.60 告警(知识库覆盖不足信号)。

#### Q22:文档更新怎么做?比如临床指南每月修订一次。【生产题】

**标准答案**:
**差分重新索引(Differential Re-indexing)**:
1. 每个文档索引时计算 content hash 存储。
2. 更新时比较新文档 hash 与存储的 hash。
3. 若变化:
   - **软删除旧 chunk**:`superseded=True` + timestamp,不硬删(审计需要)。
   - 重新 embed + 索引新文档。
4. 查询时过滤 `superseded=False`。
5. 每月跑新鲜度审计:过期文档触发维护者告警。

**高频更新场景(如药品库每日更新)**:
- CDC 管道:源系统 webhook 触发索引,近实时而非批处理。

#### Q23:检索很快但 LLM 响应慢,怎么优化?【生产题】

**标准答案(延迟预算拆解)**:
- Embedding query:~20ms
- HNSW 检索:~5ms
- LLM 生成:1-3s ← **瓶颈**

**优化策略(按优先级)**:
1. **流式生成**:返回 partial response,感知延迟大幅降低。
2. **上下文压缩**:LLMLingua 提取相关句子,prompt 缩短 50-70%,生成时间同比下降。
3. **小模型分流**:简单问候/明显跑题跳过检索。
4. **缓存**:query + top-3 chunk_ids hash,Redis 1 小时 TTL。
5. **极端场景**:常见查询类型 fine-tune 小模型,sub-200ms。

#### Q24:为什么不直接把所有文档塞进 context window,要用 RAG?【Cohere 真题】

**标准答案(两大问题)**:

**1. 成本**:
- 典型医院指南集 10000+ 页,约 250 万 token。
- 按 frontier 模型定价,每次查询仅输入 token 就 $7.50,规模化不可行。

**2. 质量(Lost in the Middle)**:
- LLM 对长 context 注意力呈 U 型,中间信息容易被忽略。
- 即使能塞下,检索质量也退化。

**RAG 的优势**:只检索 Top-5 相关 chunk(约 2000 token),模型注意力集中,成本低质量高。

#### Q25:RAG 系统怎么做 CI/CD 和回归测试?【工程题】

**标准答案**:
**Golden Set 回归**:
1. 预先标注 100-500 个(query, 期望检索 chunks, 期望答案要点)三元组。
2. 每次 pipeline 改动跑全量 golden set。
3. 对比改动前后指标:Recall@K、Faithfulness、Answer Relevancy。
4. 任一指标下降 >2% 阻断合并。

**LLM-as-Judge**:
- 用更强模型(GPT-4/Claude)对 Agent 输出打分(正确性/完整性/幻觉)。
- 降低人工标注成本,适合大规模评测。

**非确定性测试**:
- 固定 temperature=0 + 固定 seed + mock 工具返回,让输出可复现。
- 必须随机的场景跑 100 次取分布,而非单次断言。

### 3.6 结合你的 air_agent 项目回答模板

当被问到"你做过 RAG 吗",可以这样切入:

> 我正在给我的 LangGraph Agent 项目补 RAG 模块。复用已有的 SiliconFlowEmbeddingEncoder(原本用于 skill 语义路由)接 Chroma,在 basic_qa graph 下新增 knowledge-qa skill,挂 retrieve_docs 工具,把项目文档切块入库。采用递归字符切分(512 token + 50 overlap)+ Parent-Child 策略,向量 + BM25 混合检索 + RRF 融合 + BGE-Reranker 精排,用 RAGAS 评估 Faithfulness 和 Answer Relevancy。skill 路由的 Top3 候选机制(semantic-router + embedding LRU 缓存 + 后台预热)是现成的,检索和路由共用 embedding 基础设施。

这个回答体现了:
- 真实项目落地(不是 demo)
- 复用已有基础设施(工程思维)
- 全链路技术选型(切分/检索/融合/Rerank/评估)
- 与 Agent 架构集成(不是孤立 RAG)
